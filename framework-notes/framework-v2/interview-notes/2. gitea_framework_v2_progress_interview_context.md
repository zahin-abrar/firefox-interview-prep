# 5. Important Git Lessons Learned in This Thread

## 5.1 `checkout` Does Not Always Mean “Create Branch”

Important distinction:

```bash
git checkout main
```

Switches to an existing branch.

```bash
git checkout -b feature/framework-skeleton
```

Creates a new branch and switches to it.

Modern equivalent:

```bash
git switch main
```

Switch branch.

```bash
git switch -c feature/framework-skeleton
```

Create branch and switch to it.

## 5.2 Local Branch vs Remote-Tracking Branch

Example:

```text
main
remotes/origin/main
```

Meaning:

- `main` = local branch
- `remotes/origin/main` = local reference to the branch on Gitea

Do **not** delete `remotes/origin/main`. It is normal and correct.

## 5.3 Recovery From Accidental Local `origin/main` Branch

A mistaken command was run:

```bash
git checkout -b origin/main
```

This accidentally created a local branch literally named:

```text
origin/main
```

The recovery was:

```bash
git switch --detach origin/main
git switch -c main
```

Then verification:

```bash
git status
git branch -a
git log --oneline
```

Correct clean state:

```text
* main
  remotes/origin/main
```

## 5.4 When Local `main` Does Not Exist

If a clone has no local `main`, but remote `origin/main` exists, use:

```bash
git fetch origin
git switch -c main --track origin/main
```

Use this when:

```bash
git checkout main
```

fails with:

```text
error: pathspec 'main' did not match any file(s) known to git
```

## 5.5 Safe Branch Delete vs Force Delete

Safe delete:

```bash
git branch -d branch-name
```

Use this after a branch has been merged.

Force delete:

```bash
git branch -D branch-name
```

Use only when sure the branch is temporary or no longer needed.

In this thread, `test/auth-check` was force-deleted from `qa-contractor-2` because it was only a temporary authentication-test branch.

## 5.6 Pruning Deleted Remote Branch References

After a remote branch was deleted in Gitea, a stale reference still appeared locally:

```text
remotes/origin/test/auth-check
```

Cleanup command:

```bash
git fetch --prune origin
```

Final clean state:

```text
* main
  remotes/origin/main
```

Use this after PR branches are deleted remotely but still show locally.

## `utils/config_reader.py` idea

```python
import json
from pathlib import Path


def read_config(config_path: str = "config/config.json") -> dict:
    path = Path(config_path)

    if not path.exists():
        raise FileNotFoundError(f"Config file not found: {path}")

    with path.open(encoding="utf-8") as file:
        return json.load(file)
```

## `conftest.py` fixture idea

```python
import pytest
from selenium import webdriver

from utils.config_reader import read_config


@pytest.fixture(scope="session")
def config():
    return read_config()


@pytest.fixture(scope="session")
def base_url(config):
    return config["base_url"]


@pytest.fixture
def driver(config):
    browser = config.get("browser", "firefox").lower()
    headless = config.get("headless", False)

    if browser == "firefox":
        options = webdriver.FirefoxOptions()
        if headless:
            options.add_argument("-headless")
        driver = webdriver.Firefox(options=options)
    elif browser == "chrome":
        options = webdriver.ChromeOptions()
        if headless:
            options.add_argument("--headless=new")
        driver = webdriver.Chrome(options=options)
    else:
        raise ValueError(f"Unsupported browser: {browser}")

    driver.maximize_window()
    yield driver
    driver.quit()
```

# 14. Interview Explanation Notes From Work Completed

## 14.1 Why local Gitea?

> I used local Gitea to simulate a GitHub-like collaboration workflow with multiple contributors, protected main, pull requests, review comments, approvals, and branch cleanup. This helped me practice not only writing automation code, but also reviewing automation contributions the way a real distributed QA automation team would.

## 14.2 Why protected main?

> Protecting main prevents direct pushes and encourages contributors to work through feature branches and PRs. That gives maintainers a chance to review code quality, test value, stability, and maintainability before changes enter the shared branch.

## 14.3 What did PR 1 demonstrate?

> PR 1 established the framework skeleton through a contributor branch and maintainer review. It included the basic project structure, pytest configuration, dependencies, config placeholder, report directories, and `.gitignore`. Even though there were no tests yet, it validated that Pytest could discover the configured test path and that local/generated files were ignored correctly.

## 14.4 Why run `pytest --collect-only` for skeleton?

> Since no tests existed yet, running `pytest --collect-only` was enough to confirm that Pytest was installed, the virtual environment worked, `pytest.ini` was detected, and the `tests/` path was configured correctly.

## 14.5 Why virtual environments per clone?

> Each developer clone should have its own isolated Python environment. The `.venv` folder is local and ignored by Git, while `requirements.txt` acts as the shared dependency contract. This makes setup reproducible without committing environment-specific files.

## 14.6 What did the Git cleanup teach?

> The cleanup clarified the difference between local branches and remote-tracking branches, safe vs force branch deletion, and pruning stale remote references. These are practical skills for maintaining clean contributor workflows after PRs are merged and branches are deleted.
