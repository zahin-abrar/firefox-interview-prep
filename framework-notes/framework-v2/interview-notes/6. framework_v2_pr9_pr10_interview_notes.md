## 2. PR9 — Screenshot Capture on Failure

### PR title

```text
Add screenshot capture on test failure
```

### Branch

```text
feature/add-screenshot-on-failure
```

### Contributor

```text
qa-contractor-1
```

### Files touched

```text
utils/screenshot_utils.py
conftest.py
```

### Goal

Capture a screenshot automatically when a Selenium test fails, without adding screenshot code inside individual test files.

### Why this PR matters

When a UI test fails, the assertion text alone may not tell enough. A screenshot can show:

- whether the page loaded
- whether the user is logged in
- whether an error message appeared
- whether the wrong page/state is visible
- whether a locator/wait problem happened
- whether the app behavior changed

### Interview explanation

> I added screenshot capture at the framework layer so individual tests do not need to know how to take screenshots. The driver fixture handles browser lifecycle, and after the test body finishes, it checks whether the test failed. If it failed, the framework saves a timestamped screenshot before quitting the browser. This improves debuggability while keeping test files focused on behavior.

## 3. PR9 Code — `utils/screenshot_utils.py`

Expected shape:

```python
from datetime import datetime
from pathlib import Path
import re


PROJECT_ROOT = Path(__file__).resolve().parents[1]
DEFAULT_SCREENSHOT_DIR = PROJECT_ROOT / "reports" / "screenshots"


def sanitize_filename(name: str) -> str:
    return re.sub(r"[^a-zA-Z0-9_-]", "_", name)


def take_screenshot(
    driver,
    test_name: str,
    directory: str | Path = DEFAULT_SCREENSHOT_DIR
) -> str:
    screenshot_dir = Path(directory)
    screenshot_dir.mkdir(parents=True, exist_ok=True)

    timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    safe_test_name = sanitize_filename(test_name)
    screenshot_path = screenshot_dir / f"{safe_test_name}__{timestamp}.png"

    driver.save_screenshot(str(screenshot_path))

    return str(screenshot_path)
```

## 4. Question: What is `.gitkeep`?

`.gitkeep` is a placeholder file.

Git does not track empty folders. So if this folder exists:

```text
reports/screenshots/
```

but it has no files, Git ignores the folder.

To keep the folder structure in the repository, we add:

```text
reports/screenshots/.gitkeep
```

It is not a special Git feature. It is just a common convention.

Generated screenshot PNG files should usually be ignored and not committed.

## 5. Question: What is `re`?

`re` is Python’s built-in regular expression module.

In PR9, it is used here:

```python
return re.sub(r"[^a-zA-Z0-9_-]", "_", name)
```

Meaning:

```text
Find every character that is NOT a letter, number, underscore, or hyphen
and replace it with "_".
```

This is used because Pytest node IDs can contain characters such as:

```text
/ : [ ]
```

Example:

```text
tests/test_login.py::test_invalid_login_shows_error[TC_LOGIN_002]
```

Those characters can be problematic or ugly in filenames, so we sanitize them.

`screenshot_path` is a `Path` object:

Path("reports/screenshots/test_login_failed.png")

```python
str(screenshot_path)
```

## 9. Pytest Hooks

### Hook decorator

```python
@pytest.hookimpl(hookwrapper=True, tryfirst=True)
```

This tells Pytest:

> This function implements one of Pytest’s lifecycle hooks.

In PR9, it decorates:

```python
def pytest_runtest_makereport(item, call):
```

This hook runs when Pytest creates a test result report.

### `hookwrapper=True`

This makes the hook wrap around Pytest’s normal hook execution.

That is why the function uses:

```python
outcome = yield
report = outcome.get_result()
```

Meaning:

```text
Pause here.
Let Pytest create the normal report.
Then resume and inspect the result.
```

### `tryfirst=True`

This asks Pytest to run this hook implementation early compared to other hook implementations.

## 10. Fixtures vs Hooks

A strong mental model:

```text
Fixtures = provide resources to tests.
Hooks = intercept/extend Pytest lifecycle itself.
```

### Fixtures

Fixtures are about:

- setup
- teardown
- dependency injection
- shared reusable resources

A test asks for a fixture:

```python
def test_login(driver):
    ...
```

### Hooks

Hooks are about Pytest lifecycle events.

A hook is not requested by tests. Pytest calls it automatically when the matching lifecycle event happens.

### Biggest distinction

```text
Tests ask for fixtures.
Pytest calls hooks.
```

### Screenshot-on-failure relation

PR9 uses both:

```text
driver fixture → manages browser lifecycle
pytest_runtest_makereport hook → stores test result metadata
```

Together:

```text
fixture opens browser
test runs
hook stores report
fixture teardown checks report
if failed, screenshot is taken
```

## 11. Does the hook function name matter?

Yes.

Pytest recognizes hooks by official hook names.

This works:

```python
def pytest_runtest_makereport(item, call):
    ...
```

because `pytest_runtest_makereport` is a known Pytest hook.

This would not work automatically:

```python
def my_custom_report_function(item, call):
    ...
```

Pytest has predefined extension points such as:

```text
pytest_runtest_makereport
pytest_collection_modifyitems
pytest_sessionstart
pytest_sessionfinish
```

So the exact hook name matters.

## 12. Hook Code Breakdown

Code:

```python
outcome = yield
report = outcome.get_result()
setattr(item, f"rep_{report.when}", report)
```

### `outcome = yield`

Because `hookwrapper=True` is used, the hook wraps Pytest’s report generation.

This line means:

```text

Let Pytest continue and create the report.
Then come back with the result.
```

`outcome` is just a variable name. It could be `result`, but `outcome` is a common convention.

### `report = outcome.get_result()`

This gets the actual Pytest report object.

The report contains information like:

```python
report.when
report.passed
report.failed
report.skipped
```

### `setattr(item, f"rep_{report.when}", report)`

This dynamically attaches the report to the current test item.

## 13. What are `item` and `call`?

In:

```python
def pytest_runtest_makereport(item, call):
```

Pytest passes both automatically.

### `item`

`item` represents the current test case object.

It contains metadata like:

```python
item.name
item.nodeid
item.location
```

Example:

```text
item.nodeid = "tests/test_cart.py::test_add_one_item_to_cart_updates_badge"
```

### `call`

`call` represents current execution phase information.

Pytest test execution has phases:

```text
setup
call
teardown
```

In PR9, `call` is not directly used, but it is part of the official hook signature.

Mental model:

```text
item = which test?
call = which execution phase/call info?
report = what happened?
```

## 14. What does `setattr()` do?

Code:

```python
setattr(item, f"rep_{report.when}", report)
```

`setattr()` is Python’s built-in way to dynamically set an attribute on an object.

Normal way:

```python
item.rep_call = report
```

Dynamic way:

```python
setattr(item, "rep_call", report)
```

Both are basically equivalent.

### Why dynamic?

Because `report.when` can be:

```text
setup
call
teardown
```

So:

```python
f"rep_{report.when}"
```

can become:

```text
rep_setup
rep_call
rep_teardown
```

For screenshot-on-failure, we care most about:

```python
item.rep_call
```

because `call` is the actual test body phase.

## 15. Why add `request` to the `driver` fixture?

PR9 changed:

```python
def driver(config):
```

to:

```python
def driver(config, request):
```

`config` is a custom fixture.

`request` is a built-in Pytest fixture.

### What does `request` provide?

It gives access to current test/fixture context.

In PR9, we need:

```python
request.node
```

This represents the current test item using the driver fixture.

Examples:

```python
request.node.nodeid
request.node.rep_call.failed
```

### Why did errors happen when `request` was missing?

The fixture used:

```python
request.node
```

but `request` was not injected as a fixture parameter.

The error was:

```text
AttributeError: 'function' object has no attribute 'node'
```

Correct pattern:

```python
@pytest.fixture
def driver(config, request):
    ...
```

Mental shortcut:

```text
config  = execution settings
request = current test context
```

## 16. How `setattr()` and `request.node` work together

Hook:

```python
setattr(item, f"rep_{report.when}", report)
```

When `report.when == "call"`:

```python
item.rep_call = report
```

Driver fixture teardown:

```python
request.node.rep_call.failed
```

`request.node` points to the same current test item.

So:

```text
hook stores report on item
driver fixture reads that report from request.node
```

This is the bridge between hook and fixture.

## 17. Breakdown of `test_failed`

Code:

```python
test_failed = (
    hasattr(request.node, "rep_call")
    and request.node.rep_call.failed
)
```

### Meaning

> Did the actual test body fail?

### `hasattr(request.node, "rep_call")`

Checks whether the current test item has a `rep_call` attribute.

This is a safety check because `rep_call` is added dynamically by the hook.

### `and`

Both conditions must be true:

```text
rep_call exists
AND
rep_call.failed is True
```

Python uses short-circuit evaluation:

- If `hasattr(...)` is false,
- Python does not evaluate `request.node.rep_call.failed`.

This avoids `AttributeError`.

### Parentheses

The parentheses allow the expression to be written across multiple lines.

This is equivalent to:

```python
test_failed = hasattr(request.node, "rep_call") and request.node.rep_call.failed
```

It is not a tuple because there is no comma.

## 20. PR9 Git Recovery Lesson

### Mistake

The PR9 code was committed on local `main` instead of a feature branch.

State:

```text
main was ahead of origin/main by 1 commit.
```

### Recovery commands

```powershell
git checkout -b feature/add-screenshot-on-failure
git push origin feature/add-screenshot-on-failure
git checkout main
git reset --hard origin/main
```

### Why this worked

Git branch = movable pointer to a commit.

Before:

```text
origin/main → 05b1ced
main        → f1e6dc4  # PR9 commit
```

After creating feature branch:

```text
origin/main                       → 05b1ced
main                              → f1e6dc4
feature/add-screenshot-on-failure → f1e6dc4
```

After resetting main:

```text
origin/main                       → 05b1ced
main                              → 05b1ced
feature/add-screenshot-on-failure → f1e6dc4
```

The commit stayed safe on the feature branch.

## 24. PR10 Code — `utils/logger.py`

Expected shape:

```python
import logging
from pathlib import Path


PROJECT_ROOT = Path(__file__).resolve().parents[1]
DEFAULT_LOG_DIR = PROJECT_ROOT / "reports" / "logs"
DEFAULT_LOG_FILE = DEFAULT_LOG_DIR / "test_run.log"


def get_logger(name: str = "framework") -> logging.Logger:
    DEFAULT_LOG_DIR.mkdir(parents=True, exist_ok=True)

    logger = logging.getLogger(name)
    logger.setLevel(logging.INFO)

    if logger.handlers:
        return logger

    formatter = logging.Formatter(
        "%(asctime)s | %(levelname)s | %(name)s | %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S"
    )

    file_handler = logging.FileHandler(DEFAULT_LOG_FILE, encoding="utf-8")
    file_handler.setLevel(logging.INFO)
    file_handler.setFormatter(formatter)

    logger.addHandler(file_handler)

    return logger
```

## 25. Logger Code Breakdown

### Imports

```python
import logging
from pathlib import Path
```

`logging` is Python’s built-in logging module.

It allows:

```python
logger.info("Test started")
logger.error("Test failed")
```

`Path` is used to build file/folder paths cleanly.

### Path constants

```python
PROJECT_ROOT = Path(__file__).resolve().parents[1]
DEFAULT_LOG_DIR = PROJECT_ROOT / "reports" / "logs"
DEFAULT_LOG_FILE = DEFAULT_LOG_DIR / "test_run.log"
```

These create stable project-based paths:

```text
reports/logs/test_run.log
```

The path does not depend on where the terminal command is run from.

### Function definition

```python
def get_logger(name: str = "framework") -> logging.Logger:
```

This returns a `logging.Logger` object.

Default logger name:

```text
framework
```

### Avoid duplicate handlers

```python
if logger.handlers:
    return logger
```

Prevents multiple file handlers from being added if `get_logger()` is called multiple times.

Without this, log messages can appear multiple times.

### Formatter

```python
formatter = logging.Formatter(
    "%(asctime)s | %(levelname)s | %(name)s | %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S"
)
```

Controls log line style.

Example:

```text
2026-06-06 23:47:08 | INFO | framework | Starting test...
```

### File handler

```python
file_handler = logging.FileHandler(DEFAULT_LOG_FILE, encoding="utf-8")
```

Writes logs to:

```text
reports/logs/test_run.log
```

Default mode is append mode:

```python
mode="a"
```

So repeated test runs append to the same log file.

## 26. Question: Why set level in both logger and handler?

Python logging has two filters:

```text
logger level  → Should this logger accept the message at all?
handler level → Should this output destination write the message?
```

A message must pass both.

Current PR10:

```python
logger.setLevel(logging.INFO)
file_handler.setLevel(logging.INFO)
```

This means:

```text
Logger accepts INFO and above.
File handler writes INFO and above.
```

### Why both if we only write to one file?

With one file handler, it can feel redundant.

But it is future-friendly. Later, we may have:

```python
logger.setLevel(logging.DEBUG)
file_handler.setLevel(logging.DEBUG)
console_handler.setLevel(logging.INFO)
```

Meaning:

```text
File gets detailed DEBUG logs.
Console only shows cleaner INFO+ logs.
```

For PR10, setting both to `INFO` is clear and acceptable.

## 28. Question: Why use `%s` placeholders instead of f-strings in logger calls?

Example:

```python
logger.info("Test passed: %s", request.node.nodeid)
```

Instead of:

```python
logger.info(f"Test passed: {request.node.nodeid}")
```

Both can work.

But placeholder style is preferred in logging because formatting can be delayed until the logging system actually needs to write the message.

Pattern:

```python
logger.info("Message: %s", value)
```

Meaning:

```text
Here is the message template.
Here are the values.
Logging system, format them when needed.
```

## 30. Log File Append Behavior

Current code:

```python
file_handler = logging.FileHandler(DEFAULT_LOG_FILE, encoding="utf-8")
```

This is equivalent to:

```python
file_handler = logging.FileHandler(DEFAULT_LOG_FILE, mode="a", encoding="utf-8")
```

So it appends.

If the desired behavior is one fresh log per run, use:

```python
logging.FileHandler(DEFAULT_LOG_FILE, mode="w", encoding="utf-8")
```

Current decision:

```text
Append mode is acceptable for PR10.
```

Generated log files should not be committed.

## 34. Combined PR9 + PR10 Debuggability Flow

Current failure flow:

```text
Test starts
↓
Logger records test name, browser, headless mode
↓
Browser opens
↓
Test runs
↓
Pytest hook stores report as item.rep_call
↓
Driver fixture teardown resumes after yield
↓
test_failed checks request.node.rep_call.failed
↓
If failed:
    screenshot is saved under reports/screenshots/
    error log records test name and screenshot path
Else:
    pass log records test name
↓
Browser quits
↓
Browser closed log is written
```

This gives two debugging artifacts:

```text
Screenshot → visual browser state
Log        → execution context and lifecycle
```

## 35. Strong Interview Narrative

A polished explanation:

> I intentionally added debug support in two small PRs. First, I added screenshot capture on failure so failed Selenium tests produce visual evidence before the browser closes. Then I added centralized framework logging so the run captures the test name, browser, headless mode, pass/fail result, screenshot path for failures, and teardown completion. I kept both features in the framework layer rather than individual tests, so tests stay readable and the debug behavior is consistent across the suite.

## 36. If Asked: Why not Allure in the same PR?

Answer:

> I kept screenshot capture and logging as separate PRs because each one changes framework behavior and deserves focused review. Adding Allure at the same time would mix dependency changes, reporting commands, possible attachments, and failure handling. I prefer incremental PRs: first screenshot files, then logs, then Allure reporting, and finally optional screenshot attachments to Allure.

## 37. If Asked: What did you learn from PR9?

Answer:

> PR9 helped me understand Pytest’s deeper lifecycle. Fixtures manage resources like the browser, but hooks let us intercept Pytest’s internal reporting lifecycle. The screenshot feature needed both: the hook stored the test result report, and the fixture teardown used that result to decide whether to capture a screenshot before quitting the browser.

## 38. If Asked: What did you learn from PR10?

Answer:

> PR10 helped me understand centralized logging design. I learned why we use a reusable logger, why duplicate handlers must be avoided, why logger and handler levels both exist, and why log messages should include enough context to debug failures without becoming too noisy.
