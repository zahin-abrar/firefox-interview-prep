## 2. PR3 — BasePage Interview Notes

### 2.1 What PR3 added

PR3 added:

```text
pages/base_page.py
```

The `BasePage` centralized common Selenium operations:

- open URL
- wait for visible element
- wait for clickable element
- click
- type text
- get text
- check visibility

### 2.2 Why BasePage exists

Without BasePage, every page object might repeat raw Selenium logic:

```python
driver.find_element(...).click()
driver.find_element(...).send_keys(...)
WebDriverWait(...).until(...)
```

With BasePage, page classes can call reusable helpers:

```python
self.click(self.LOGIN_BUTTON)
self.type_text(self.USERNAME_INPUT, username)
self.is_visible(self.INVENTORY_LIST)
```

This improves:

- maintainability
- consistency
- readability
- reliability through explicit waits
- PR review clarity

### 2.3 BasePage code discussed

```python
from selenium.common.exceptions import TimeoutException
from selenium.webdriver.remote.webdriver import WebDriver
from selenium.webdriver.remote.webelement import WebElement
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.support.ui import WebDriverWait


class BasePage:
    """
    Base class for all Page Objects.

    Centralizes common Selenium actions so page classes do not repeat
    raw WebDriver wait/click/type/text logic.
    """

    def __init__(self, driver: WebDriver, timeout: int = 10):
        self.driver = driver
        self.timeout = timeout

    def open_url(self, url: str) -> None:
        """Open the given URL in the current browser session."""
        self.driver.get(url)

    def find_visible(self, locator: tuple[str, str]) -> WebElement:
        """Wait until an element is visible and return it."""
        return WebDriverWait(self.driver, self.timeout).until(
            EC.visibility_of_element_located(locator)
        )

    def find_clickable(self, locator: tuple[str, str]) -> WebElement:
        """Wait until an element is clickable and return it."""
        return WebDriverWait(self.driver, self.timeout).until(
            EC.element_to_be_clickable(locator)
        )

    def click(self, locator: tuple[str, str]) -> None:
        """Click an element after waiting for it to be clickable."""
        self.find_clickable(locator).click()

    def type_text(self, locator: tuple[str, str], text: str) -> None:
        """Clear an input field and type text into it."""
        element = self.find_visible(locator)
        element.clear()
        element.send_keys(text)

    def get_text(self, locator: tuple[str, str]) -> str:
        """Return visible text from an element."""
        return self.find_visible(locator).text

    def is_visible(self, locator: tuple[str, str]) -> bool:
        """Return True if an element becomes visible within the timeout."""
        try:
            self.find_visible(locator)
            return True
        except TimeoutException:
            return False
```

## 3. Question: Why is `driver` inside BasePage if fixture provides it?

### User confusion

The `driver` is created in the Pytest fixture in `conftest.py`, so why does `BasePage` also have `self.driver`?

### Explanation

The fixture creates and provides the driver. BasePage does not create it.

BasePage only receives the already-created driver and stores a reference to it:

```python
def __init__(self, driver, timeout=10):
    self.driver = driver
    self.timeout = timeout
```

Flow:

```text
conftest.py driver fixture
    creates browser
        ↓
test receives driver
        ↓
test creates page object: LoginPage(driver, ...)
        ↓
LoginPage passes driver to BasePage
        ↓
BasePage stores it as self.driver
        ↓
BasePage methods use self.driver to click/type/wait
```

### Interview answer

> The WebDriver is still created by the Pytest fixture. BasePage only stores that fixture-created driver so all page object methods can use the same browser session. This keeps browser lifecycle management in fixtures and UI interaction logic in page objects.

## 4. Question: What is `self`?

### Simple definition

In Python class methods, `self` means:

```text
this particular object instance
```

Example:

```python
class Person:
    def __init__(self, name):
        self.name = name

    def say_hello(self):
        print(f"Hello, I am {self.name}")

person1 = Person("Abrar")
person2 = Person("Mike")
```

When calling:

```python
person1.say_hello()
```

Python internally behaves roughly like:

```python
Person.say_hello(person1)
```

So inside the method, `self` is `person1`.

### Applying it to BasePage/LoginPage

When we create:

```python
login_page = LoginPage(driver, base_url)
```

inside that object:

```python
self.driver = driver
self.base_url = base_url
```

means:

```text
store driver and base_url inside this LoginPage object
```

When we later call:

```python
login_page.click(LoginPage.LOGIN_BUTTON)
```

inside `click()`:

```python
self.find_clickable(locator).click()
```

`self` means the same `login_page` object.

### Mental model

```text
self = this object
self.driver = this object's browser driver
self.find_visible() = call this object's helper method
```

### Interview answer

> In Python, `self` refers to the current object instance. In Page Object Model, when I create a page object like `LoginPage(driver)`, the object stores the Selenium driver as `self.driver`. Then all methods in that page object can use the same browser session through `self.driver`.

## 5. Question: Do expected conditions return the element?

### Question

Do these Selenium functions return the element associated with the locator?

```python
EC.element_to_be_clickable(locator)
EC.visibility_of_element_located(locator)
```

### Explanation

Yes. In our usage, both return a Selenium `WebElement` when the condition succeeds.

Example:

```python
element = WebDriverWait(self.driver, self.timeout).until(
    EC.visibility_of_element_located(locator)
)
```

This means:

```text
wait until the element exists and is visible
then return that WebElement
```

That is why this works:

```python
def type_text(self, locator, text):
    element = self.find_visible(locator)
    element.clear()
    element.send_keys(text)
```

### Mental model

```text
EC.visibility_of_element_located(locator)
    waits for visible element
    returns WebElement

EC.element_to_be_clickable(locator)
    waits for visible + enabled element
    returns WebElement

WebDriverWait(...).until(...)
    keeps polling until it receives a truthy value
    returns that truthy value
```

```python
from selenium.webdriver.common.by import By

from pages.base_page import BasePage


class LoginPage(BasePage):
    USERNAME_INPUT = (By.ID, "user-name")
    PASSWORD_INPUT = (By.ID, "password")
    LOGIN_BUTTON = (By.ID, "login-button")

    def __init__(self, driver, base_url: str, timeout: int = 10):
        super().__init__(driver, timeout)
        self.base_url = base_url

    def open(self) -> None:
        self.open_url(self.base_url)

    def enter_username(self, username: str) -> None:
        self.type_text(self.USERNAME_INPUT, username)

    def enter_password(self, password: str) -> None:
        self.type_text(self.PASSWORD_INPUT, password)

    def click_login_button(self) -> None:
        self.click(self.LOGIN_BUTTON)

    def login(self, username: str, password: str) -> None:
        self.enter_username(username)
        self.enter_password(password)
        self.click_login_button()
```

## 7. Question: How does `super().__init__(driver, timeout)` work?

### Code

```python
def __init__(self, driver, base_url: str, timeout: int = 10):
    super().__init__(driver, timeout)
    self.base_url = base_url
```

### Explanation

`LoginPage` inherits from `BasePage`:

```python
class LoginPage(BasePage):
```

So `LoginPage` can use BasePage methods:

```python
self.open_url()
self.type_text()
self.click()
self.find_visible()
```

When this runs:

```python
login_page = LoginPage(driver, base_url, timeout=timeout)
```

Python enters `LoginPage.__init__()`.

At that point:

```text
self      = the new LoginPage object
driver    = Selenium WebDriver from fixture
base_url  = SauceDemo URL
timeout   = timeout value from config or default
```

Then:

```python
super().__init__(driver, timeout)
```

calls:

```python
BasePage.__init__(self, driver, timeout)
```

That stores:

```python
self.driver = driver
self.timeout = timeout
```

Then this line stores LoginPage-specific data:

```python
self.base_url = base_url
```

### Important note

`super().__init__(driver, timeout)` does **not** create a separate BasePage object. It initializes the BasePage part of the same LoginPage object.

### Mental model

```text
LoginPage(driver, base_url, timeout)
        ↓
LoginPage receives all three
        ↓
super().__init__(driver, timeout)
        ↓
BasePage stores self.driver and self.timeout
        ↓
LoginPage stores self.base_url
        ↓
LoginPage can now use BasePage methods
```

### Interview answer

> `LoginPage` inherits from `BasePage`, so I call `super().__init__(driver, timeout)` to initialize the shared BasePage state, mainly the WebDriver instance and wait timeout. Then `LoginPage` stores its own page-specific data, such as `base_url`.

## 8. Question: How are fixtures accessed?

### User confusion

We are not explicitly calling fixtures, so how does the test get `driver`, `base_url`, and `config`?

### Explanation

Pytest calls fixtures automatically when it sees their names in the test function parameters.

Example:

```python
def test_standard_user_can_login(driver, base_url, config):
    ...
```

Pytest sees:

```text
driver
base_url
config
```

Then it looks for fixtures with the same names, usually in `conftest.py`.

### Behind the scenes

```text
1. Test needs driver, base_url, config
2. Pytest finds config fixture
3. config fixture reads config.json and returns dict
4. Pytest finds base_url fixture
5. base_url needs config, so Pytest gives config to base_url
6. base_url returns config["base_url"]
7. Pytest finds driver fixture
8. driver needs config, so Pytest gives config to driver
9. driver fixture opens Firefox/Chrome and yields driver
10. Pytest calls the test function with real values
11. Test runs
12. After test finishes, driver fixture continues after yield and calls driver.quit()
```

### Page objects do not access fixtures directly

Page objects only receive values from tests or fixtures.

```text
Pytest fixture system
    ↓
injects driver/base_url/config into test or fixture
    ↓
test/fixture creates LoginPage(driver, base_url, timeout)
    ↓
LoginPage/BasePage uses self.driver
```

### Interview answer

> In Pytest, fixtures are requested by adding their names as parameters to the test function. Pytest automatically finds matching fixture functions, runs them, and injects their returned or yielded values into the test. The Page Object itself does not call the fixture; it only receives the already-created driver from the test or fixture.

## 10. Question: How does Python `assert` work?

### Code discussed

```python
assert "inventory.html" in driver.current_url, (
    f"Expected user to reach inventory page, but current URL was: "
    f"{driver.current_url}"
)
```

### Question 1: Are we checking an HTML file?

No. We are checking the browser URL, not the DOM or Inspect Element.

After successful SauceDemo login, browser URL becomes something like:

```text
https://www.saucedemo.com/inventory.html
```

So:

```python
"inventory.html" in driver.current_url
```

means:

```text
Does the current browser URL contain inventory.html?
```

### Question 2: Are we printing the message?

No. The message is not printed when the test passes.

It is a failure message shown only if the assertion fails.

### Question 3: What are the assert components?

Python assert syntax:

```python
assert condition, failure_message
```

In this code:

```python
assert "inventory.html" in driver.current_url, (
    f"Expected user to reach inventory page, but current URL was: "
    f"{driver.current_url}"
)
```

Component 1:

```python
"inventory.html" in driver.current_url
```

This evaluates to `True` or `False`.

Component 2:

```python
(
    f"Expected user to reach inventory page, but current URL was: "
    f"{driver.current_url}"
)
```

This is the failure message.

### Important improvement in PR5

After adding `InventoryPage`, the login assertion was improved from URL assertion to UI assertion:

```python
assert inventory_page.is_inventory_list_visible(), (
    "Expected inventory list to be visible after successful login."
)
```

This is better because it verifies that the inventory UI actually loaded, not only that the URL changed.

```python
from selenium.webdriver.common.by import By

from pages.base_page import BasePage


class InventoryPage(BasePage):
    """
    Page Object for the SauceDemo inventory page.

    Responsibilities:
    - represent the post-login product listing page
    - verify inventory list visibility
    - provide product count for tests
    """

    INVENTORY_LIST = (By.CLASS_NAME, "inventory_list")
    INVENTORY_ITEMS = (By.CLASS_NAME, "inventory_item")

    def __init__(self, driver, timeout: int = 10):
        super().__init__(driver, timeout)

    def is_inventory_list_visible(self) -> bool:
        """Return True if the inventory list is visible."""
        return self.is_visible(self.INVENTORY_LIST)

    def get_inventory_item_count(self) -> int:
        """Return the number of products displayed on the inventory page."""
        self.find_visible(self.INVENTORY_LIST)
        return len(self.driver.find_elements(*self.INVENTORY_ITEMS))
```

## 12. Question: Why does LoginPage return InventoryPage?

### Design decision

Instead of:

```python
login_page.login(...)
return InventoryPage(driver, timeout=timeout)
```

we changed successful login to:

```python
inventory_page = login_page.login(...)
```

where `login()` returns `InventoryPage`.

### Why this makes sense

After successful login, SauceDemo navigates from login page to inventory page.

```text
LoginPage
   ↓ successful login
InventoryPage
```

So this is a logical Page Object Model transition.

### Key point

This does not create a new browser.

```python
return InventoryPage(self.driver, timeout=self.timeout)
```

means:

```text
use the same browser session
create a new page object that represents the page the browser is now on
```

### Mental model

```text
driver = real browser
LoginPage(driver) = interface for login page
login action changes browser state
InventoryPage(driver) = interface for new page after login
```

### Important caution

`login()` returning `InventoryPage` only makes sense for **successful login**.

For negative login tests later, add a separate method such as:

```python
def attempt_login(self, username, password) -> None:
    ...
```

or:

```python
def submit_login(self, username, password) -> None:
    ...
```

This method should not return `InventoryPage` because invalid login remains on LoginPage.

### Interview answer

> I designed successful login to return `InventoryPage` because after valid credentials, the browser navigates from the login page to the inventory page. The returned object uses the same WebDriver session, so it represents the current browser state after login. For invalid login tests, I would use a separate method that does not return InventoryPage.

## 13. Question: What is `(By.CLASS_NAME, "inventory_item")`?

### Explanation

This is a Python tuple.

```python
INVENTORY_ITEMS = (By.CLASS_NAME, "inventory_item")
```

It contains two values:

```text
Item 1 → By.CLASS_NAME
Item 2 → "inventory_item"
```

Selenium frameworks often store locators as tuples because a locator needs two pieces:

```text
locator strategy
locator value
```

Example:

```python
LOGIN_BUTTON = (By.ID, "login-button")
```

### Why tuple instead of list?

Locators are normally fixed/immutable values. Tuples fit that purpose well.

## 14. Question: Why use `*self.INVENTORY_ITEMS`?

### Code

```python
len(self.driver.find_elements(*self.INVENTORY_ITEMS))
```

### Explanation

`find_elements()` expects two separate arguments:

```python
driver.find_elements(By.CLASS_NAME, "inventory_item")
```

But our variable contains one tuple:

```python
INVENTORY_ITEMS = (By.CLASS_NAME, "inventory_item")
```

If we write:

```python
driver.find_elements(self.INVENTORY_ITEMS)
```

Python passes the whole tuple as one argument:

```text
argument 1 → (By.CLASS_NAME, "inventory_item")
argument 2 → missing
```

Using `*` unpacks the tuple:

```python
driver.find_elements(*self.INVENTORY_ITEMS)
```

becomes:

```python
driver.find_elements(By.CLASS_NAME, "inventory_item")
```

### Simple example

```python
def add(a, b):
    return a + b

numbers = (2, 3)

add(*numbers)  # same as add(2, 3)
```

### Interview answer

> The locator is stored as a tuple containing the locator strategy and value. Selenium’s `find_elements()` expects those as two separate arguments, so I use `*` to unpack the tuple into separate arguments.

## 15. Question: Why can BasePage pass locator tuple directly to expected conditions?

### Code

```python
def find_visible(self, locator: tuple[str, str]) -> WebElement:
    return WebDriverWait(self.driver, self.timeout).until(
        EC.visibility_of_element_located(locator)
    )
```

### Explanation

The difference is what the called function expects.

`EC.visibility_of_element_located()` expects one argument:

```text
locator tuple
```

So this is correct:

```python
EC.visibility_of_element_located(locator)
```

But raw Selenium `find_elements()` expects two separate arguments:

```python
driver.find_elements(By.CLASS_NAME, "inventory_item")
```

So tuple unpacking is needed there:

```python
driver.find_elements(*self.INVENTORY_ITEMS)
```

### Mental model

```text
Expected condition → wants tuple directly
Raw driver method  → wants tuple unpacked
```

## 16. Question: Why `timeout=timeout` but not `driver=driver` and `base_url=base_url`?

### Code

```python
login_page = LoginPage(driver, base_url, timeout=timeout)
```

### Explanation

The constructor is:

```python
def __init__(self, driver, base_url: str, timeout: int = 10):
```

Python accepts both positional and keyword arguments.

In this call:

```python
LoginPage(driver, base_url, timeout=timeout)
```

- `driver` is positional
- `base_url` is positional
- `timeout=timeout` is keyword

This is a common style:

```text
required arguments → positional
optional/config arguments → keyword
```

### Fully explicit version

For learning and PR review clarity, this is also valid and maybe clearer:

```python
login_page = LoginPage(
    driver=driver,
    base_url=base_url,
    timeout=timeout
)
```

### Python rule

Once you use a keyword argument, arguments after it must also be keyword arguments.

Valid:

```python
LoginPage(driver, base_url, timeout=timeout)
```

Valid:

```python
LoginPage(driver=driver, base_url=base_url, timeout=timeout)
```

Invalid:

```python
LoginPage(driver=driver, base_url, timeout)
```

## 21. Interview Explanation Snippets

### 21.1 Explain the current framework progression

> I built the framework incrementally through small PRs. First I created the skeleton, then added browser/config fixtures, then a BasePage with explicit waits, then a LoginPage and valid login smoke test, and then an InventoryPage with a logged-in fixture. This helped me practice both framework design and realistic PR review workflow.

### 21.2 Explain BasePage

> BasePage centralizes common Selenium operations such as waiting, clicking, typing, and reading text. Instead of repeating raw driver logic in every page class, page objects use these helper methods. This improves maintainability and reduces flaky timing issues because waits are handled consistently.

### 21.3 Explain fixtures

> Fixtures separate setup and teardown from test logic. In this framework, the `driver` fixture creates and quits the browser, `config` loads JSON settings, `base_url` provides the application URL, and `logged_in_inventory_page` prepares an authenticated state for tests that need it.

### 21.4 Explain Page Object Model

> Page Object Model separates test scenario logic from UI interaction details. Test files describe what behavior we validate, while page classes describe how to interact with the UI through locators and methods.

### 21.5 Explain LoginPage returning InventoryPage

> Since a successful login navigates to the inventory page, the `login()` method returns an `InventoryPage` object using the same driver. This makes the page transition explicit and allows tests or fixtures to continue from the correct page object after login.

### 21.6 Explain `logged_in_inventory_page`

> The `logged_in_inventory_page` fixture composes existing fixtures and page objects. It receives `driver`, `base_url`, and `config`, logs in as a standard user through `LoginPage`, and returns `InventoryPage`. This avoids repeating login setup in every inventory/cart test.

### 21.7 Explain smoke vs setup test

> The setup test verifies that the browser and base URL can open correctly. The actual smoke tests validate user-facing critical flows, such as login and inventory visibility. That is why running `pytest -m smoke` may deselect the setup test if it is not marked as smoke.

### 21.8 Explain tuple unpacking

> Locators are stored as tuples like `(By.CLASS_NAME, "inventory_item")`. Expected conditions accept the tuple directly, but raw Selenium methods like `find_elements()` expect strategy and value as separate arguments, so `*locator` unpacks the tuple into separate arguments.

### 21.9 Explain why explicit waits instead of sleep

> Explicit waits wait for meaningful UI states such as visibility or clickability. `time.sleep()` blindly pauses execution, making tests slower and often still flaky if the page takes longer than expected.
