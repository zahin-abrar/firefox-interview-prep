### Why including the refactor in PR7 made sense

Initially, `test_standard_user_can_login()` manually created and opened the login page:

```python
timeout = config.get("default_timeout", 10)

login_page = LoginPage(
    driver=driver,
    base_url=base_url,
    timeout=timeout
)
login_page.open()
```

After adding negative login tests, both positive and negative login tests needed to start from the login page.

Instead of repeating this setup in multiple tests, we created:

```python
@pytest.fixture
def login_page(driver, base_url, config):
    timeout = config.get("default_timeout", 10)

    page = LoginPage(
        driver=driver,
        base_url=base_url,
        timeout=timeout
    )
    page.open()

    return page
```

This was a small, related refactor.

### Final fixture chain

```text
driver + base_url + config
        ↓
login_page
        ↓
logged_in_inventory_page
```

### Why fixture composition is good

The lower-level fixture creates a reusable page state:

```text
login_page → opened login page
```

The higher-level fixture builds from it:

```text
logged_in_inventory_page → opened login page + successful login + InventoryPage
```

This avoids duplicate setup and makes fixture responsibilities clearer.

### Important concept: fixtures are injected into tests, not page objects

Pytest injects fixture values into test functions or other fixtures by matching parameter names.

Example:

```python
def test_standard_user_can_login(login_page, config):
```

Pytest sees `login_page` and `config`, finds those fixtures, runs them, and passes their returned values into the test.

Page objects do not directly receive fixtures from Pytest. They receive normal Python arguments from tests or fixtures.

Flow:

```text
Pytest fixture system
→ injects fixture values into test/fixture
→ test/fixture creates page object
→ page object receives normal arguments
```

### Important concept: `login_page` fixture is not a Page Object feature

`login_page` is a Pytest convenience layer.

It creates and prepares the Page Object:

```text
create LoginPage
pass driver/base_url/timeout
open the login page
return LoginPage
```

The `LoginPage` class itself still only knows Selenium/page behavior.

### Why `login()` and `attempt_login()` are separate

Positive login and negative login have different expectations.

```text
login()
→ assumes success
→ returns InventoryPage

attempt_login()
→ does not assume success
→ stays on LoginPage
→ used for error validation
```

### LoginPage additions

```python
ERROR_MESSAGE = (By.CSS_SELECTOR, "[data-test='error']")

def attempt_login(self, username: str, password: str) -> None:
    self.enter_username(username)
    self.enter_password(password)
    self.click_login_button()

def get_error_message(self) -> str:
    return self.get_text(self.ERROR_MESSAGE)
```

### Parametrized negative login test before JSON

PR7 originally used inline parametrization:

```python

@pytest.mark.regression
@pytest.mark.parametrize(
    "username,password,expected_error",
    [
        (
            "locked_out_user",
            "secret_sauce",
            "Epic sadface: Sorry, this user has been locked out."
        ),
        (
            "standard_user",
            "wrong_password",
            "Epic sadface: Username and password do not match any user in this service"
        ),
        (
            "",
            "secret_sauce",
            "Epic sadface: Username is required"
        ),

            "standard_user",

            "Epic sadface: Password is required"
```

### Why parametrization was useful

The flow was the same in all negative cases:

```text

enter username
enter password
click login

```

Only the input and expected message changed.

Parametrization avoids four duplicate test functions.

I then refactored the successful login test to use that fixture and added parametrized negative login tests. I also separated successful login from failed login behavior: `login()` returns `InventoryPage`, while `attempt_login()` does not assume navigation and is used for error validation.

### JSON reader utility

```python
import json
from pathlib import Path


PROJECT_ROOT = Path(__file__).resolve().parents[1]


def read_json(file_path: str | Path) -> list[dict]:
    """
    Read a JSON file and return its parsed content.

    Args:
        file_path: Relative or absolute path to the JSON file.

    Returns:
        list[dict]: Parsed JSON data.
    """
    path = Path(file_path)

    if not path.is_absolute():
        path = PROJECT_ROOT / path

    if not path.exists():
        raise FileNotFoundError(f"JSON test data file not found: {path}")

    with path.open(encoding="utf-8") as file:
        return json.load(file)
```

## 5. User Questions and Clarifications From This Thread

### Question 1: Fixtures are passed to test functions, not page objects — correct?

User understanding:

> Fixtures are passed to test functions, not the page objects.

Clarification:

Yes. Pytest injects fixtures into tests and other fixtures by matching function parameter names.

Example:

```python
def test_standard_user_can_login(login_page, config):
```

Here:

```text
login_page → fixture
config     → fixture
```

A page object like `LoginPage` does not directly receive fixtures from Pytest. It receives normal Python arguments when the test or fixture creates it:

```python
LoginPage(driver=driver, base_url=base_url, timeout=timeout)
```

Strong mental model:

```text
Pytest fixture system
→ test/fixture function
→ page object constructor
→ page object methods
```

### Question 2: Why create `login_page` fixture?

User understanding:

> Since two login tests need the login page to open, we are creating a login_page fixture to reuse one block of setup code instead of passing driver, base_url, config to every login test.

Clarification:

Correct.

Before:

```python
def test_standard_user_can_login(driver, base_url, config):
    timeout = config.get("default_timeout", 10)

    login_page = LoginPage(
        driver=driver,
        base_url=base_url,
        timeout=timeout
    )
    login_page.open()
```

After:

```python
def test_standard_user_can_login(login_page, config):
```

The fixture still depends on `driver`, `base_url`, and `config`, but the test no longer needs to manually create/open the page.

Important refinement:

```text
login_page fixture replaces driver/base_url/config only for tests that need an opened LoginPage.
It does not replace those fixtures globally in the framework.
```

### Question 3: What does `Path(__file__).resolve().parents[1]` mean?

Code:

```python
PROJECT_ROOT = Path(__file__).resolve().parents[1]
```

Breakdown:

#### `__file__`

Path to the current Python file.

Inside:

```text
utils/json_reader.py
```

`__file__` points to something like:

```text
D:\...\saucedemo-pytest-automation\utils\json_reader.py
```

#### `Path(__file__)`

Converts the string path into a `Path` object.

#### `.resolve()`

Turns it into an absolute, normalized path.

#### `.parents`

Gives parent folders.

For:

```text
saucedemo-pytest-automation/utils/json_reader.py
```

parents are:

```text
parents[0] = saucedemo-pytest-automation/utils
parents[1] = saucedemo-pytest-automation
```

#### `.parents[1]`

Goes two levels up from the file and gives the project root.

So:

```python
PROJECT_ROOT = Path(__file__).resolve().parents[1]
```

means:

```text
Start from utils/json_reader.py
go up to utils/
go up again to project root/
save that location
```

Why useful?

It lets the framework reliably load:

```text
test_data/login_data.json
```

even if the test is run from a different terminal working directory.

### Question 4: What does `read_json(file_path: str | Path) -> list[dict]` mean?

Code:

```python
def read_json(file_path: str | Path) -> list[dict]:
```

Breakdown:

#### `def read_json(...)`

Defines a function named `read_json`.

#### `file_path`

The function parameter.

#### `file_path: str | Path`

Type hint meaning:

```text
file_path can be a string OR a pathlib.Path object
```

The pipe operator `|` means **or** in modern Python type hints.

Equivalent older style:

```python
from typing import Union

def read_json(file_path: Union[str, Path]) -> list[dict]:
```

Modern style:

```python
def read_json(file_path: str | Path) -> list[dict]:
```

This syntax works in Python 3.10+.

#### `-> list[dict]`

Return type hint.

It means the function is expected to return:

```text
a list of dictionaries
```

This matches the JSON login data shape.

Important note:

Type hints help developers, IDEs, and static checkers. They do not strictly enforce runtime behavior by themselves.

### Question 5: What does this parametrization mean?

Code:

```python
@pytest.mark.parametrize(
    "login_case",
    NEGATIVE_LOGIN_DATA,
    ids=[case["case_id"] for case in NEGATIVE_LOGIN_DATA]
)
```

Meaning:

```text
Run the same test once for each item in NEGATIVE_LOGIN_DATA.
Pass each item into the test using the parameter name login_case.
Use case_id as the readable test name in Pytest output.
```

If `NEGATIVE_LOGIN_DATA` has 4 dictionaries, Pytest runs the test 4 times.

### Question 6: Is `login_case` a fixture?

No.

In:

```python
def test_invalid_login_shows_error(login_page, login_case):
```

there are two different mechanisms:

```text
login_page → Pytest fixture from conftest.py
login_case → parametrized data from @pytest.mark.parametrize
```

### Question 7: What is `ids`?

`ids` controls how each parametrized test case appears in Pytest output.

Without `ids`, Pytest might show generic or noisy names.

With:

```python
ids=[case["case_id"] for case in NEGATIVE_LOGIN_DATA]
```

output becomes:

```text
test_invalid_login_shows_error[TC_LOGIN_002]
test_invalid_login_shows_error[TC_LOGIN_003]
test_invalid_login_shows_error[TC_LOGIN_004]
test_invalid_login_shows_error[TC_LOGIN_005]
```

This improves readability and debugging.

`ids` does not affect the actual test logic.

### Question 8: Is `[case["case_id"] for case in NEGATIVE_LOGIN_DATA]` a special kind of for loop?

Yes. It is called a **list comprehension**.

This:

```python
[case["case_id"] for case in NEGATIVE_LOGIN_DATA]
```

is equivalent to:

```python
ids = []

for case in NEGATIVE_LOGIN_DATA:
    ids.append(case["case_id"])
```

If the data is:

```python
[
    {"case_id": "TC_LOGIN_002"},
    {"case_id": "TC_LOGIN_003"}
]
```

the list comprehension produces:

```python
["TC_LOGIN_002", "TC_LOGIN_003"]
```

## 6. Current Technical Concepts to Revise

### 6.1 Fixture injection

Pytest fixtures are injected by parameter name.

```python
def test_example(driver):
    ...
```

Pytest sees `driver`, finds the fixture, runs it, and passes its return/yield value into the test.

### 6.2 Fixture composition

One fixture can depend on another fixture.

```python
@pytest.fixture
def logged_in_inventory_page(login_page, config):
    ...
```

This means Pytest first prepares `login_page` and `config`, then runs `logged_in_inventory_page`.

### 6.3 Page Object responsibility

Page classes should answer:

```text
How do we interact with this page?
```

Test files should answer:

```text
What behavior are we validating?
```

### 6.4 BasePage responsibility

`BasePage` centralizes common Selenium actions:

- open URL
- wait for visible element
- wait for clickable element
- click
- type text
- get text
- visibility check

It avoids duplicate raw WebDriver calls across page classes.

### 6.5 Parametrization

Use parametrization when:

- the flow is the same
- inputs differ
- expected outputs differ

Avoid parametrization when:

- scenarios are fundamentally different
- test body becomes full of conditionals
- data hides too much behavior

### 6.6 JSON data-driven testing

JSON is useful when:

- data is simple
- structure is dictionary-like
- Git diff readability matters
- you want to separate test logic and test data

### 6.7 Stable test output

Using `ids` in parametrization makes test output meaningful and easier to debug.

Good output:

```text
test_invalid_login_shows_error[TC_LOGIN_003]
```

Less useful output:

```text
test_invalid_login_shows_error[login_case1]
```

## 8. Interview Answer Bank

### 8.1 Why did you add a cart badge smoke test?

> After validating login and inventory visibility, I wanted the smoke suite to cover the first meaningful e-commerce interaction. Adding one item to the cart and verifying the badge count gives quick confidence that the inventory page supports a core user action.

### 8.2 Why did you not add CartPage immediately?

> I kept PR6 small and focused. Since the badge is visible on the inventory page and the test does not navigate to the cart page, adding the behavior to `InventoryPage` was enough. I would introduce `CartPage` when validating cart contents, removal, checkout, or cart-specific UI.

### 8.3 Why create a `login_page` fixture?

> Multiple tests need the same starting state: an opened login page with the configured driver, base URL, and timeout. The `login_page` fixture centralizes that setup so tests do not repeat page creation and opening logic.

### 8.4 Do fixtures get passed to page objects?

> Not directly. Pytest injects fixtures into test functions or other fixtures by matching parameter names. A test or fixture then creates the page object and passes normal Python arguments like driver, base URL, and timeout.

### 8.5 Why separate `login()` and `attempt_login()`?

> `login()` represents a successful login workflow and returns the next page object, `InventoryPage`. For negative login tests, success is not expected, so `attempt_login()` performs the same UI actions without assuming navigation. That keeps the page transition logic accurate.

### 8.6 Why use parametrization for negative login?

> The negative login scenarios share the same flow but use different inputs and expected error messages. Parametrization avoids duplicated test functions while keeping each case explicit.

### 8.7 Why move negative login data to JSON?

> JSON separates test data from test logic. The test remains focused on behavior, while the input combinations are easier to review and extend in a dedicated data file.

### 8.8 Why use `ids` in parametrized tests?

> `ids` gives each parametrized case a readable name in Pytest output. Instead of generic or noisy parameter names, we see IDs like `TC_LOGIN_002`, which makes debugging and PR review easier.

### 8.9 Why use `Path(__file__).resolve().parents[1]`?

> It calculates the project root based on the utility file location. This makes file loading stable because the path does not depend on where the terminal or IDE launches Pytest from.

### 8.10 Why use `str | Path`?

> It means the function accepts either a string path or a `pathlib.Path` object. The pipe operator is modern Python syntax for a union type, meaning “or”.

### 8.11 Why not add Excel in PR8?

> JSON was enough for the current negative login data because the data is simple and Git-friendly. Excel can be useful for QA-friendly tabular data later, but adding it now would increase scope without much extra interview value.

### 8.12 What would you review in these PRs as maintainer?

> I would check whether each PR is focused, uses fixtures properly, avoids duplication, keeps page interactions inside page objects, uses stable locators and explicit waits, has meaningful assertions, and improves readability or debuggability without over-abstracting.

It uses Page Object Model to separate page interactions from test logic, Pytest fixtures to handle browser setup, config loading, and reusable page states, and markers to organize smoke, regression, negative, and data-driven tests.  
>
> The current flow includes opening SauceDemo, logging in as a standard user, verifying the inventory page, adding a product to the cart, checking the cart badge, and validating negative login scenarios.  
>
> I also practiced a Gitea-based PR workflow with simulated contributors, protected main, feature branches, reviews, and merges. The purpose was not only to write automation but to practice how automation changes should be structured, reviewed, and explained in a team context.

## 10. Current Framework Walkthrough — More Detailed Version

> The framework starts with `conftest.py`, where fixtures manage config loading, browser lifecycle, login page setup, and authenticated inventory state. The `driver` fixture creates the browser and handles teardown. The `login_page` fixture creates and opens the LoginPage. The `logged_in_inventory_page` fixture builds on top of `login_page` and returns an authenticated InventoryPage.  
>
> Page classes live under `pages/`. `BasePage` centralizes Selenium actions like explicit waits, clicking, typing, reading text, and checking visibility. `LoginPage` represents the SauceDemo login page and includes both successful login and negative login methods. `InventoryPage` represents the product listing page and currently supports inventory validation and a simple cart badge check.  
>
> Tests live under `tests/`. The successful login, inventory, and cart tests are marked as smoke and regression. Negative login tests are parametrized and use JSON data from `test_data/login_data.json`, loaded through `utils/json_reader.py`. This keeps test logic separate from test data and makes failures easier to identify using readable case IDs.  
>
> The project is developed through local Gitea to simulate a realistic team workflow: contributor branches, PRs, review, protected main, merge, and sync across clones.

Debuggability is a real automation engineering concern. When a Selenium test fails, a screenshot helps identify whether the failure is:

- product issue
- locator issue
- wait/timing issue
- test data issue
- environment/browser issue
