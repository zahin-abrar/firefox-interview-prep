# Framework V2 Implementation Guide — Selenium Pytest + Gitea PR Review Lab

**Project context:** Mozilla Firefox Round 2 technical deep-dive preparation  
**Target role:** Firefox Software Test Engineering Student Worker  
**Automation target website:** [SauceDemo](https://www.saucedemo.com/)  
**Primary learning goal:** Build a realistic, maintainable Selenium/Pytest framework while practicing Git branching, pull requests, PR review, and multi-contributor workflow using local Gitea.

## 0. How to Use This Guide

This document is a **master implementation guide**, not a one-day checklist.

The goal is to create a clean Framework V2 project that can support:

- Selenium WebDriver automation with Python.
- Pytest fixtures, markers, and parametrization.
- Page Object Model architecture.
- SauceDemo login, inventory, cart, and checkout test scenarios.
- JSON and Excel-based data-driven tests.
- Screenshot and logging support.
- Room for Allure reporting.
- Local Gitea PR review simulation.
- Later GitHub publishing.
- Later CI integration.

Do **not** try to complete everything in Day 3. Day 3 should begin the foundation: repository strategy, Gitea setup, branching workflow, skeleton framework, first Page Object, first tests, and PR review habits.

Gitea lets you practice locally:

- Branching.
- Pull requests.

GitHub is better for:

- Public/private portfolio hosting.

- Source code.
- Commit history.
- Branches.
- Tags.


Use:



Use clear, small commits.

Examples:

```text

Add LoginPage object for SauceDemo login screen
Add smoke test for valid SauceDemo login
Add negative login parametrized tests
Refactor browser fixture to support Chrome and Firefox

```

### 4.4 Pull Request Flow

Normal flow:

```text
1. Create branch from main
2. Implement one focused change
3. Run relevant tests locally
4. Commit and push branch
5. Open PR in Gitea
6. Reviewer checks code and leaves comments
7. Contributor updates branch
8. Reviewer approves
9. Merge to main
10. Delete feature branch if no longer needed
```

## 6. SauceDemo Test Case Selection Strategy

### 6.1 Test Selection Principles

Automate tests that are:

- Stable.
- Repeatable.
- Important to core user flow.
- Useful for regression.
- Easy to diagnose on failure.
- Good examples of framework design.

Avoid initially:

- Too many low-value UI-only checks.
- Brittle visual layout assertions.
- Overly long end-to-end tests that validate everything.
- Tests that depend on execution order.

## 7. Pytest Marker Strategy

### 7.1 Marker List

Use these markers in `pytest.ini`:

```ini
[pytest]
markers =
    smoke: critical fast tests for build validation
    regression: broader safety-net tests
    negative: validation/error-handling tests
    e2e: longer end-to-end user-flow tests
    data_driven: tests using external data sources such as JSON or Excel
    slow: tests that take longer than normal
```

### 7.2 Marker Usage Examples

```python
import pytest

@pytest.mark.smoke
@pytest.mark.regression
def test_valid_user_can_login(driver):
    ...
```

```python
@pytest.mark.negative
@pytest.mark.regression
@pytest.mark.parametrize("username,password,expected_error", [...])
def test_invalid_login_shows_error(driver, username, password, expected_error):
    ...
```

### 7.3 Useful Commands

Run smoke tests:

```bash
pytest -m smoke
```

Run regression tests:

```bash
pytest -m regression
```

Run negative tests:

```bash
pytest -m negative
```

Run everything except slow tests:

```bash
pytest -m "not slow"
```

Run with verbose output:

```bash
pytest -v
```

Run one file:

```bash
pytest tests/test_login.py -v
```

## 8. Fixture Strategy

### 8.1 Fixture Design Goals

Fixtures should make tests cleaner by handling:

- Browser setup.
- Browser teardown.
- Browser selection.
- Base URL loading.
- Login setup when needed.
- Screenshots on failure.
- Config loading.

### 8.2 Recommended Initial Fixtures

| Fixture | Scope | Purpose |
|---|---|---|
| `config` | session | Load config once |
| `driver` | function | Start/quit browser per test |
| `base_url` | session | Provide SauceDemo URL |
| `login_page` | function | Return LoginPage object |
| `logged_in_inventory_page` | function | Log in and return InventoryPage |

### 8.3 Browser Fixture Sketch

```python
import pytest
from selenium import webdriver

@pytest.fixture
def driver(config):
    browser = config.get("browser", "firefox").lower()
    headless = config.get("headless", False)

    if browser == "firefox":
        options = webdriver.FirefoxOptions()
        if headless:
            options.add_argument("-headless")
        driver = webdriver.Firefox(options=options)
    elif browser == "chrome":
        options = webdriver.ChromeOptions()
        if headless:
            options.add_argument("--headless=new")
        driver = webdriver.Chrome(options=options)
    else:
        raise ValueError(f"Unsupported browser: {browser}")

    driver.maximize_window()
    yield driver
    driver.quit()
```

### 8.4 Login Fixture Sketch

```python
@pytest.fixture
def logged_in_inventory_page(driver, config):
    login_page = LoginPage(driver, config["base_url"])
    login_page.open()
    inventory_page = login_page.login_as(
        config["users"]["standard"]["username"],
        config["users"]["standard"]["password"],
    )
    return inventory_page
```

### 8.5 Fixture Review Questions

When reviewing fixture-related PRs, ask:

- Is setup/teardown reliable?
- Does the fixture hide too much test behavior?
- Is the fixture name clear?
- Is test state isolated?
- Does it support local and future CI execution?
- Does it avoid hardcoded environment assumptions?

## 9. Parametrization Strategy

### 9.1 Why Parametrization Matters

Parametrization avoids duplicate tests when the flow is the same but input data differs.

Good candidates:

- Negative login combinations.
- Checkout validation fields.
- Sorting options.
- Product names.

Bad candidates:

- Completely different workflows.
- Tests with too much branching logic.
- Cases where each scenario needs separate explanation.

### 9.2 Example: Negative Login Parametrization

```python
import pytest

@pytest.mark.negative
@pytest.mark.regression
@pytest.mark.parametrize("username,password,expected_error", [
    ("locked_out_user", "secret_sauce", "locked out"),
    ("standard_user", "wrong_password", "do not match"),
    ("", "secret_sauce", "Username is required"),
    ("standard_user", "", "Password is required"),
])
def test_invalid_login_shows_error(login_page, username, password, expected_error):
    login_page.open()
    login_page.login(username, password)
    assert expected_error in login_page.get_error_message()
```

### 9.3 Review Rule

If a test has multiple almost-identical functions differing only by input values, consider parametrization.

If a parametrized test has many conditional branches inside the test body, split it into separate tests.

```python
from openpyxl import load_workbook


def read_excel_as_dicts(file_path: str, sheet_name: str) -> list[dict]:
    workbook = load_workbook(file_path)
    sheet = workbook[sheet_name]

    rows = list(sheet.iter_rows(values_only=True))
    headers = rows[0]

    data = []
    for row in rows[1:]:
        data.append(dict(zip(headers, row)))

    return data
```

5. Add Excel-based data-driven test as a separate learning enhancement.

## 11. Page Object Model Strategy

### 11.1 POM Design Rule

Test files should answer:

> What scenario are we validating?

Page classes should answer:

> How do we interact with this page?

### 11.2 BasePage Responsibilities

`BasePage` should contain reusable Selenium actions:

- Open URL.
- Wait for visibility.
- Wait for clickability.
- Click.
- Type text.
- Get text.
- Check element visibility.
- Select dropdown option.
- Maybe take screenshot.

Avoid making `BasePage` too clever.

### 11.3 BasePage Sketch

```python
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC


class BasePage:
    def __init__(self, driver, timeout=10):
        self.driver = driver
        self.timeout = timeout

    def open_url(self, url):
        self.driver.get(url)

    def find_visible(self, locator):
        return WebDriverWait(self.driver, self.timeout).until(
            EC.visibility_of_element_located(locator)
        )

    def find_clickable(self, locator):
        return WebDriverWait(self.driver, self.timeout).until(
            EC.element_to_be_clickable(locator)
        )

    def click(self, locator):
        self.find_clickable(locator).click()

    def type_text(self, locator, text):
        element = self.find_visible(locator)
        element.clear()
        element.send_keys(text)

    def get_text(self, locator):
        return self.find_visible(locator).text

    def is_visible(self, locator):
        try:
            self.find_visible(locator)
            return True
        except Exception:
            return False
```

## 12. Locator Strategy

### 12.1 Locator Principles

Prefer:

- `id`.
- `name`.
- Stable `data-test` attributes.
- Stable CSS selectors.

Avoid when possible:

- Absolute XPath.
- Index-based XPath.
- Long brittle CSS chains.
- Locators based only on visual position.

### 12.2 SauceDemo Locator Examples

Likely useful SauceDemo locator style:

## 13. Reporting Strategy: Screenshots, Logs, and Allure

### 13.1 Screenshot Strategy

Screenshots should be captured on failure.

Recommended location:

```text

```

Filename format:

```text
<test_name>__<YYYYMMDD_HHMMSS>.png
```

Example:

```text

```

### 13.2 Screenshot Utility Sketch

```python
from datetime import datetime
from pathlib import Path
import re


def sanitize_filename(name: str) -> str:
    return re.sub(r"[^a-zA-Z0-9_-]", "_", name)


def take_screenshot(driver, test_name: str, directory="reports/screenshots") -> str:
    Path(directory).mkdir(parents=True, exist_ok=True)
    timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
    filename = f"{sanitize_filename(test_name)}__{timestamp}.png"
    file_path = Path(directory) / filename
    driver.save_screenshot(str(file_path))
    return str(file_path)
```

This can be added later after the first tests are stable.

## 15. PR Review Checklist

Use this when reviewing automation PRs in Gitea.

### 15.1 Test Value

- [ ] Is the scenario worth automating?
- [ ] Is it stable and repeatable?
- [ ] Does it cover a meaningful business/user flow?
- [ ] Is it correctly marked as smoke/regression/negative/e2e?

### 15.2 Test Readability

- [ ] Is the test name clear?
- [ ] Can someone understand the scenario without reading every implementation detail?
- [ ] Is the test focused on one main behavior?
- [ ] Are assertions meaningful?

### 15.3 Page Object Model

- [ ] Are page interactions inside page classes?
- [ ] Are test assertions mostly in test files?
- [ ] Are locators centralized inside page objects?
- [ ] Are method names user-action oriented?
- [ ] Is there no giant god-page object?

### 15.4 Selenium Reliability

- [ ] Are explicit waits used?
- [ ] Are hard sleeps avoided?
- [ ] Are locators stable?
- [ ] Are browser/window/frame assumptions valid?
- [ ] Is test data isolated enough?

### 15.5 Fixtures and Setup

- [ ] Is browser setup handled by fixtures?
- [ ] Is teardown reliable?
- [ ] Is the fixture scope appropriate?
- [ ] Does the test avoid depending on previous tests?

### 15.6 Data and Config

- [ ] Are credentials/config values not scattered across tests?
- [ ] Is test data readable?
- [ ] Is parametrization used where helpful?
- [ ] Is Excel/JSON use justified and not overcomplicated?

### 15.7 Debuggability

- [ ] Can a failure be diagnosed from assertion message/log/screenshot?
- [ ] Is the assertion specific enough?
- [ ] Are screenshots captured on failure, if the infrastructure exists?
- [ ] Are logs helpful but not noisy?

### 15.8 Maintainability

- [ ] Is there duplicate code that should become a helper?
- [ ] Is there over-abstraction that hides simple behavior?
- [ ] Is the change small enough to review?
- [ ] Are names consistent?

## 16. PR Review Lab Scenarios

### 16.1 Scenario A — Bad Login Test

Contributor creates a PR with:

- Hardcoded credentials in the test.
- `time.sleep(5)`.
- Absolute XPath.
- No Page Object.
- Broad assertion like `assert "Products" in driver.page_source`.

Reviewer feedback should mention:

- Replace hard sleep with explicit wait.
- Move locators/actions into `LoginPage`.
- Prefer stable locators like `id` or `data-test`.
- Move credentials to config/test data.
- Use a specific assertion such as inventory container visibility or URL check.
- Add marker: `smoke` and `regression`.

### 16.2 Scenario B — Over-Abstracted Page Object

Contributor creates a PR with:

- Generic methods like `do_action(action_name)`.
- Too many conditionals inside page object.
- Test becomes hard to read.

Reviewer feedback should mention:

- Prefer clear user-action methods.
- Avoid abstraction that hides behavior.
- Keep page objects simple and readable.

### 16.3 Scenario C — Duplicate Negative Login Tests

Contributor creates four separate invalid login test functions with duplicated code.

Reviewer feedback should mention:

- Use `pytest.mark.parametrize`.
- Keep scenario table readable.
- Make expected error explicit per case.

### 16.4 Scenario D — Excel Data Added Too Early

Contributor adds Excel DDT before simple tests and fixtures are stable.

Reviewer feedback should mention:

- Good idea, but sequence matters.
- Stabilize framework skeleton first.
- Add Excel as an enhancement after core tests pass.

## 19. Interview Explanation Notes

### 19.1 Framework Walkthrough

Use this structure:

> The goal of Framework V2 is to practice a realistic Selenium/Pytest automation setup using SauceDemo. I structured it around Page Object Model, Pytest fixtures, markers, parametrization, and reusable utilities. I also used local Gitea to simulate a real team workflow with branches, pull requests, protected main, and PR review. This helped me practice not only writing tests, but reviewing automation contributions for maintainability and reliability.

### 19.2 Why Gitea

> I used Gitea locally to simulate a GitHub-like workflow with multiple contributors. It allowed me to practice feature branches, pull requests, review comments, and protected main without depending on a public remote repository.

### 19.3 Why SauceDemo

> SauceDemo is small but realistic enough for automation practice. It includes login, inventory, cart, checkout, sorting, and negative validation paths, so I can demonstrate smoke, regression, negative, and end-to-end test design without needing a large application.

### 19.4 Why Page Object Model

> Page Object Model separates page interaction logic from test scenario logic. If the UI changes, I can update locators and actions in the page class instead of editing many tests.

### 19.5 Why Fixtures

> Fixtures keep setup and teardown separate from test logic. In this framework, fixtures manage browser lifecycle, config loading, and optional preconditions such as logged-in state.

### 19.6 Why Markers

> Markers help organize test execution. Smoke tests give fast feedback for critical flows, while regression tests provide broader coverage. Negative and data-driven markers make targeted execution easier.

### 19.7 Why Parametrization

> Parametrization reduces duplicate test code when the same flow needs to be validated with multiple input combinations. It is especially useful for login validation and checkout form errors.

### 19.8 Why Excel Data-Driven Testing

> Excel can be useful when QA teams are familiar with maintaining test cases in tabular form. I would use it carefully for stable input combinations, while keeping the test logic readable and avoiding data files that hide too much behavior.

### 19.9 How You Would Review a Contributor PR

> I would review whether the test adds value, uses stable locators, avoids hard sleeps, has meaningful assertions, follows Page Object Model, uses fixtures properly, avoids duplication, handles data cleanly, and provides enough debug information through logs or screenshots.
