### `utils/config_reader.py`

```python
import json
from pathlib import Path


PROJECT_ROOT = Path(__file__).resolve().parents[1]
DEFAULT_CONFIG_PATH = PROJECT_ROOT / "config" / "config.json"


def read_config(config_path: str | Path = DEFAULT_CONFIG_PATH) -> dict:
    path = Path(config_path)

    if not path.exists():
        raise FileNotFoundError(f"Config file not found: {path}")

    with path.open(encoding="utf-8") as file:
        return json.load(file)
```

### `conftest.py`

```python
import pytest
from selenium import webdriver

from utils.config_reader import read_config


@pytest.fixture(scope="session")
def config():
    return read_config()


@pytest.fixture(scope="session")
def base_url(config):
    return config["base_url"]


@pytest.fixture
def driver(config):
    browser = config.get("browser", "firefox").lower()
    headless = config.get("headless", False)

    if browser == "firefox":
        options = webdriver.FirefoxOptions()
        if headless:
            options.add_argument("-headless")
        driver = webdriver.Firefox(options=options)

    elif browser == "chrome":
        options = webdriver.ChromeOptions()
        if headless:
            options.add_argument("--headless=new")
        driver = webdriver.Chrome(options=options)

    else:
        raise ValueError(f"Unsupported browser: {browser}")

    driver.maximize_window()
    yield driver
    driver.quit()
```

## 5. User Question 1 — Why does `test_smoke_setup.py` work without `import pytest`?

### Question

> I noticed in my previous framework files, I needed to import pytest. But here even without importing pytest seems to recognize the test file. Why is that? From the previous framework code, was there any reason to import pytest there?

### Explanation

Pytest does **not** require `import pytest` just to discover and run a test.

Pytest discovers tests based on naming conventions such as:

```text
test_*.py files
def test_* functions
Test* classes
```

So this works without importing Pytest:

```python
def test_browser_can_open_base_url(driver, base_url):
    driver.get(base_url)
    assert "saucedemo" in driver.current_url
```

because it uses:

```text
plain Python function
plain assert
fixture names as parameters
```

### When is `import pytest` needed?

You need `import pytest` when the file directly uses Pytest objects/features:

```python
import pytest

@pytest.mark.smoke
def test_something():
    ...
```

or:

```python
import pytest

@pytest.mark.parametrize("username,password", [...])
def test_login(username, password):
    ...
```

or:

```python
with pytest.raises(ValueError):
    ...
```

### Why the previous framework imported `pytest`

The previous framework used:

```python
@pytest.mark.usefixtures("setup_and_teardown", "log_on_failure")
class BaseTest:
    pass
```

and:

```python
@pytest.mark.parametrize(...)
def test_login_with_valid_credentials(...):
    ...
```

Those decorators require `import pytest`.

### Interview answer

> Pytest does not need to be imported just to discover a test. It discovers tests through naming conventions and can inject fixtures by parameter name. I only need `import pytest` when I directly use Pytest APIs like `@pytest.mark.parametrize`, `@pytest.mark.smoke`, `@pytest.fixture`, `pytest.raises`, or `pytest.mark.usefixtures`.

## 6. User Question 2 — How do `driver` and `base_url` get passed directly into the test?

### Question

> We can directly use `driver`, `base_url` as function parameters and it can access driver and base URL. How is that happening? We haven't used anything to indicate that we need fixtures.

### Explanation

This is Pytest fixture injection.

When Pytest sees:

```python
def test_browser_can_open_base_url(driver, base_url):
    ...
```

it reads the parameter names:

```text
driver
base_url
```

Then it searches for fixtures with those names.

It finds them in `conftest.py`:

```python
@pytest.fixture(scope="session")
def base_url(config):
    return config["base_url"]

@pytest.fixture
def driver(config):
    ...
    yield driver
    driver.quit()
```

Then Pytest resolves and injects them automatically.

### Conceptual flow

```text
test asks for driver and base_url
↓
Pytest finds driver fixture
↓
Pytest finds base_url fixture
↓
Both need config fixture
↓
Pytest runs config fixture once
↓
Pytest passes config into base_url and driver fixtures
↓
base_url returns URL string
↓
driver yields browser object
↓
Pytest calls test_browser_can_open_base_url(driver_object, base_url_string)
```

### Old framework comparison

Old style:

```text
fixture → request.cls.driver → test uses self.driver
```

New style:

```text
fixture → yield driver → test receives driver parameter
```

### Interview answer

> Pytest resolves fixtures by parameter name. If a test function has a parameter named `driver`, Pytest looks for a fixture named `driver`. If that fixture depends on another fixture, such as `config`, Pytest resolves that dependency first. This lets tests request exactly what they need without manually calling setup functions.

## 7. User Question 3 — Are we not going for class-based framework implementation?

### Question

> So we are not going for a class-based framework implementation now? I thought for POM we need to implement classes for abstraction.

### Explanation

There are two different meanings of “class-based” here.

### 1. Page Object classes — YES

POM still uses classes:

```python
class BasePage:
    ...

class LoginPage(BasePage):
    ...
```

This is the abstraction layer.

### 2. Test classes with `BaseTest` inheritance — not now

The previous framework used:

```python
class TestLogin(BaseTest):
    def test_login_with_valid_credentials(self):
        home_page = HomePage(self.driver)
```

Framework V2 currently uses function-based tests:

```python
def test_browser_can_open_base_url(driver, base_url):
    ...
```

This is a test style decision, not a POM decision.

### Key mental model

```text
Page Objects  → class-based
Tests         → currently function-based
```

### Why use function-based tests for now?

- clearer fixture dependencies
- no hidden `self.driver`
- easier for contributors to understand
- more direct Pytest style
- less inheritance wiring

### Interview answer

> POM still uses classes. What changed is the test style. In my old framework, tests were class-based and inherited from `BaseTest`, which attached the driver as `self.driver`. In Framework V2, I am keeping Page Objects class-based but starting with function-based Pytest tests and direct fixture injection. This keeps test dependencies visible while still preserving POM abstraction.

## 8. User Question 4 — Why `yield driver` now, but only `yield` before?

### Question

> Previously we only used `yield` and had to use `request.cls.driver = driver`. Now that we are not using test classes, we can't use `request.cls.driver` and therefore need to specify we are yielding driver to the test function?

### Explanation

Yes. That is exactly right.

Previous framework:

```python
request.cls.driver = driver
yield
driver.quit()
```

Here, the fixture passes the driver by side effect:

```text
Attach driver to class → test uses self.driver
```

Framework V2:

```python
yield driver
driver.quit()
```

Here, the fixture gives the driver directly to the test function:

```text
Yield driver → test receives driver parameter
```

### Difference at the yield point

```python
yield
```

means:

```text
pause fixture, run test, resume teardown
```

```python
yield driver
```

means:

```text
pause fixture, give driver to test, run test, resume teardown
```

### Important nuance

`yield` is not used because of function-based tests. It is used because fixtures need setup and teardown.

The function-based difference is that we yield the object directly instead of attaching it to a class.

### Interview answer

> In my earlier framework, the fixture attached the driver to the test class using `request.cls.driver`, so the test accessed it as `self.driver`. In Framework V2, because I’m using direct fixture injection, the driver fixture yields the WebDriver object directly. Pytest passes that yielded object into the test function. The teardown concept is the same; only the delivery mechanism changed.

## 9. User Question 5 — What are browser `options`?

### Question

> My next confusion is with options. This is a new concept for me. Could you elaborate on this feature?

### Explanation

Browser options are browser startup settings.

Examples:

```python
options = webdriver.FirefoxOptions()
```

```python
options = webdriver.ChromeOptions()
```

Then they are passed when creating the driver:

```python
driver = webdriver.Firefox(options=options)
```

This means:

```text
Start Firefox with these custom startup settings.
```

### What options can control

Browser options can configure things like:

```text
headless mode
window size
browser profile
download directory
proxy settings
extensions
certificate behavior
browser binary path
browser-specific command-line arguments
```

In PR2, options are only used for:

```text
headless mode
```

### Headless mode

Headless mode means the browser runs without a visible UI window.

Useful for:

- CI/CD pipelines
- servers without display
- automated validation where watching the UI is not needed

In config:

```json
"headless": false
```

means show the browser window.

```json
"headless": true
```

means run without a visible browser window.

### Interview answer

> Browser options are configuration objects passed to Selenium before the browser starts. They allow us to control startup behavior such as headless mode, download settings, profiles, proxies, or browser-specific arguments. In PR2 I used options to make headless execution configurable through `config.json`.

## 10. User Question 6 — Why Firefox uses `-headless` but Chrome uses `--headless=new`?

### Question

> For Firefox we used `-headless` but for Chrome it is `--headless=new`. Why is this difference?

### Explanation

Firefox and Chrome are different browser programs. Their command-line flags are not always identical.

For Firefox:

```python
options.add_argument("-headless")
```

For Chrome in our current guide:

```python
options.add_argument("--headless=new")
```

This is browser-specific syntax.

Chrome historically had older and newer headless modes. `--headless=new` explicitly selected the newer headless mode in modern Chrome versions. Current Chrome may also support plain `--headless`, but our PR2 followed the implementation guide’s suggested fixture sketch.

### Practical framework decision

Keep this for PR2:

```python
options.add_argument("--headless=new")
```

Do not derail PR2 for Chrome flag modernization. This can be reviewed later if needed.

### Interview answer

> Browser options use browser-specific command-line flags. Firefox and Chrome do not always use the same syntax. For Firefox, the headless flag is commonly `-headless`; for Chrome, modern Selenium examples often use `--headless=new` to request Chrome’s newer headless mode. The important design point is that headless behavior is controlled from config, not hardcoded in tests.

## 11. User Question 7 — Are fixture-decorated functions still functions?

### Question

> I also could not understand the `config` param in `base_url` and `driver` functions. Are these still called functions or should they be called fixtures now that they are under `@pytest.fixture`?

### Explanation

They are both, depending on perspective.

Python sees:

```python
def config():
    ...
```

as a function.

Pytest sees:

```python
@pytest.fixture
def config():
    ...
```

as a fixture provider.

So in normal testing conversation, we call them:

```text
config fixture
base_url fixture
driver fixture
```

Technically, they are Python functions registered as fixtures.

### Good wording

```text
Python function decorated as a Pytest fixture
```

or simply:

```text
fixture
```

### Interview answer

> A fixture is still a Python function, but the `@pytest.fixture` decorator registers it with Pytest. After that, Pytest can inject it into tests or other fixtures by name. So I would usually call `config`, `base_url`, and `driver` fixtures, even though syntactically they are functions.

## 12. User Question 8 — Does `base_url(config)` mean config is manually passed?

### Question

> Does it mean these functions expect the `config` function to be passed as argument?

### Explanation

No manual passing is needed.

When Pytest sees:

```python
@pytest.fixture(scope="session")
def base_url(config):
    return config["base_url"]
```

it understands:

```text
base_url fixture depends on config fixture
```

Pytest resolves this automatically:

```text
Run config fixture
↓
Get config dictionary
↓
Pass dictionary into base_url fixture
↓
base_url returns config["base_url"]
```

Similarly:

```python
@pytest.fixture
def driver(config):
    browser = config.get("browser", "firefox").lower()
```

means:

```text
driver fixture depends on config fixture
```

### Interview answer

> When a fixture has another fixture name as a parameter, Pytest treats that as a dependency. I do not call `base_url(config)` manually. Pytest runs the `config` fixture first and injects its return value into `base_url` and `driver` automatically.

## 13. Config: INI vs JSON

### User question

> In my previous framework, I had `config.ini`. Now we are using JSON. Is this best practice? What are the benefits?

### Balanced answer

INI is valid for simple flat config.

Old config:

```ini
[basic info]
browser=chrome
url=https://tutorialsninja.com/demo/
```

That is simple and readable.

JSON is a better fit for Framework V2 because the config is more structured:

```json
{
  "base_url": "https://www.saucedemo.com/",
  "browser": "firefox",
  "headless": false,
  "default_timeout": 10,
  "users": {
    "standard": {
      "username": "standard_user",
      "password": "secret_sauce"
    },
    "locked": {
      "username": "locked_out_user",
      "password": "secret_sauce"
    }
  }
}
```

### Benefits of JSON here

| Benefit | Explanation |
|---|---|
| Nested data | Users, environments, and browser settings are easier to group. |
| Better type handling | `false` becomes Python `False`, `10` becomes integer `10`. |
| Future test data alignment | The guide later uses JSON test data. |
| Review-friendly | Git diffs show structured changes clearly. |
| Easy Python parsing | `json.load()` returns dictionaries/lists naturally. |

### JSON disadvantages

- no comments
- strict syntax
- missing comma or wrong quotes breaks parsing

### Interview answer

> INI is fine for simple flat configuration, like browser and URL. For Framework V2, JSON is a better fit because the config includes nested data such as users, browser settings, headless mode, and timeout. JSON preserves booleans and numbers better and aligns with later JSON-based test data. I still keep `pytest.ini` for Pytest settings because Pytest expects that style.

## 16. Fixture Lifecycle: `return` vs `yield`

### `return` fixture

```python
@pytest.fixture
def config():
    return read_config()
```

Good when there is no teardown.

### `yield` fixture

```python
@pytest.fixture
def driver():
    driver = webdriver.Firefox()
    yield driver
    driver.quit()
```

Needed when there is teardown.

### Browser fixture lifecycle

```text
create browser
maximize browser
yield browser to test
test runs
quit browser
```

### Why not `return driver`?

If we return the driver, there is no code after the test to reliably quit the browser.

With `yield`, Pytest resumes the fixture after the test and runs cleanup.

### Interview answer

> I use `yield` in the driver fixture because browser setup and teardown are both needed. Code before `yield` prepares the browser, the yielded driver is used by the test, and code after `yield` quits the browser. For fixtures that only provide data, like config, `return` is enough.

## 17. Fixture Scopes

### Current scopes

```python
@pytest.fixture(scope="session")
def config():
    ...
```

```python
@pytest.fixture(scope="session")
def base_url(config):
    ...
```

```python
@pytest.fixture
def driver(config):
    ...
```

### Meaning

| Fixture | Scope | Why |
|---|---|---|
| `config` | session | Load config once per test run. |
| `base_url` | session | URL does not change per test. |
| `driver` | function/default | Fresh browser per test for isolation. |

### Interview answer

> I used session scope for config and base URL because they are stable data for the whole run. I kept the driver fixture function-scoped so each test gets a clean browser session and teardown is reliable. This reduces test dependency and shared-state problems.

## 24. General Selenium/Pytest Interview Cheat Sheet

### What is a fixture?

> A fixture is a reusable setup/teardown or data provider function registered with Pytest. Tests request fixtures by naming them as parameters.

### Why use fixtures for Selenium?

> Fixtures centralize browser setup and teardown, reduce duplicate code, and keep tests focused on behavior.

### Why function-scoped driver?

> Each test gets a fresh browser, reducing test dependency and shared state.

### Why session-scoped config?

> Config is stable during the run, so loading it once is enough.

### Why `yield` in driver fixture?

> It allows setup before the test and teardown after the test.

### Why root-level `conftest.py`?

> Browser/config fixtures are framework-wide, so root-level placement makes them available to all tests.

### Why JSON config?

> JSON supports structured config, nested users, booleans, numbers, and aligns with future JSON test data.

### Why browser options?

> Options configure browser startup behavior, such as headless mode.

### Why not add Allure now?

> Reporting should come after core browser/page/test flow is stable. Otherwise it distracts from foundational design.

## 29. Common Interview Questions and Strong Answers

### Q: Why use Pytest fixtures?

> Fixtures separate setup and teardown from test logic. In Selenium, they are useful for browser lifecycle, config loading, test data setup, and reusable preconditions. This keeps tests clean and reduces duplicated setup code.

### Q: How does Pytest know which fixture to use?

> Pytest resolves fixtures by name. If a test function has a parameter named `driver`, Pytest searches for a fixture named `driver` and injects its value.

### Q: Why use `yield` in a fixture?

> `yield` allows setup before the test and teardown after the test. For browser fixtures, the code before `yield` launches the browser, the yielded object is used by the test, and the code after `yield` quits the browser.

### Q: Why avoid hard sleeps?

> Hard sleeps wait blindly and either slow tests down or still fail if the UI takes longer. Explicit waits wait for meaningful conditions like visibility or clickability.

### Q: Why use Page Object Model?

> POM separates page interaction logic from test scenario logic. If the UI changes, we update locators or actions in the page class instead of changing many tests.

### Q: Why not use `BaseTest` anymore?

> `BaseTest` is valid, but direct fixture injection makes dependencies clearer in this new framework. Tests explicitly declare what they need, such as `driver`, `base_url`, or `config`.

### Q: Are function-based tests less professional?

> No. Function-based tests are idiomatic Pytest. POM still uses classes for page objects; the choice of function-based or class-based tests is separate.

### Q: Why use Gitea?

> Gitea lets me simulate a real PR workflow locally with multiple contributors, protected main, review comments, approvals, merges, and branch cleanup.

### Q: Why use SauceDemo?

> SauceDemo is small but covers useful e-commerce flows: login, inventory, cart, checkout, sorting, negative cases, and logout. It is enough to demonstrate framework architecture without creating a huge project.
