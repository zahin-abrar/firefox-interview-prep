## 3. PR15 Interview Notes — Successful Checkout E2E

### What PR15 added

PR15 added the successful checkout flow:

```text
log in
→ add Sauce Labs Backpack
→ open cart
→ verify cart/product state
→ checkout
→ enter first name, last name, postal code
→ continue
→ verify overview page
→ finish
→ verify checkout complete page and success message
```

### Main files

```text
pages/cart_page.py
pages/checkout_page.py
tests/test_checkout.py
```

### Marker choice

```python
@pytest.mark.e2e
@pytest.mark.regression
```

### Why `e2e`?

Because this test validates a complete user journey across several app areas:

```text
InventoryPage
→ CartPage
→ CheckoutPage
→ Checkout Complete
```

### Why not smoke?

Checkout is important, but it is longer than the smallest critical build checks. Login/cart badge/logout are better smoke candidates. Checkout is better as `e2e + regression`.

### Design explanation

`CartPage.checkout()` returns `CheckoutPage` because clicking checkout transitions the user to a new page/flow.

This follows the existing pattern:

```text
LoginPage.login(...) → InventoryPage
InventoryPage.go_to_cart() → CartPage
CartPage.checkout() → CheckoutPage
```

### Interview answer

> PR15 added the first complete checkout E2E flow. I kept the checkout-specific locators and actions inside CheckoutPage, cart navigation inside CartPage, and assertions in the test layer. This keeps the test readable as a user scenario while keeping page interaction details reusable and maintainable.

### Implementation difference from original plan

Original suggestion:

```python
ERROR_MESSAGE = (By.CSS_SELECTOR, "[data-test='error']")
```

Actual implementation:

```python
ERROR_MESSAGE = (By.CLASS_NAME, "error-message-container")
```

Reason:

- User could not find `[data-test='error']`.
- `error-message-container` was visible/usable in the DOM.

Interview framing:

> I originally considered a data-test locator, but during inspection I could not find it for this element, so I used the stable class available in the DOM. The important thing is that the locator is verified and centralized in the page object.

### No `submit_customer_information()` wrapper

Original suggestion:

```python
checkout_page.submit_customer_information(...)
```

Actual implementation:

```python
checkout_page.enter_customer_information(...)
checkout_page.continue_checkout()
```

Reason:

- The two existing methods already express the flow clearly.
- Adding a wrapper would be optional and slightly premature.
- The test remains explicit and readable.

Interview framing:

> I decided not to add a submit wrapper because enter customer information and continue checkout were already simple and readable. I would add a wrapper later only if the same sequence becomes repeated in many tests.

```python
def test_checkout_requires_customer_information(
```

## 5. Pytest Parametrize `ids` Explanation

### User question

In PR16, the test used:

```python
ids=[
    "missing-first-name",
    "missing-last-name",
    "missing-postal-code",
]
```

Pytest output showed:

```text
tests/test_checkout.py::test_checkout_requires_customer_information[missing-first-name] PASSED
tests/test_checkout.py::test_checkout_requires_customer_information[missing-last-name] PASSED
tests/test_checkout.py::test_checkout_requires_customer_information[missing-postal-code] PASSED
```

The question was:

> How does Pytest know to use `ids` in the test name?

### Explanation

`ids` is a built-in optional argument of `pytest.mark.parametrize`.

Example:

```python
@pytest.mark.parametrize(
    "first_name,last_name,postal_code,expected_error",
    [
        ("", "Zahin", "18057", "Error: First Name is required"),
        ("Abrar", "", "18057", "Error: Last Name is required"),
        ("Abrar", "Zahin", "", "Error: Postal Code is required"),
    ],
    ids=[
        "missing-first-name",
        "missing-last-name",
        "missing-postal-code",
    ],
)
```

Pytest maps each data row to the matching ID:

| Data row | ID |
|---|---|
| `("", "Zahin", "18057", ...)` | `missing-first-name` |
| `("Abrar", "", "18057", ...)` | `missing-last-name` |
| `("Abrar", "Zahin", "", ...)` | `missing-postal-code` |

So Pytest generates:

```text
test_checkout_requires_customer_information[missing-first-name]
test_checkout_requires_customer_information[missing-last-name]
test_checkout_requires_customer_information[missing-postal-code]
```

### Rule

The number of IDs should match the number of parameter rows.

```text
3 data rows
3 ids
```

### Interview answer

> The `ids` argument gives each generated parametrized test case a readable name. Pytest maps each ID to the corresponding parameter set and appends it inside square brackets in the output. This makes failures easier to identify, especially in data-driven tests.

## 7. Selenium `Select` Helper — Detailed Explanation

### Why `Select` was used

SauceDemo sorting uses an HTML `<select>` dropdown.

Selenium provides the `Select` helper specifically for `<select>` elements.

Import:

```python
from selenium.webdriver.support.ui import Select
```

Typical code:

```python
def select_sort_option(self, value: str):
    sort_dropdown = self.find_visible(self.SORT_DROPDOWN)
    Select(sort_dropdown).select_by_value(value)
```

### Breakdown

```python
sort_dropdown = self.find_visible(self.SORT_DROPDOWN)
```

This waits until the dropdown is visible and returns the Selenium WebElement.

```python
Select(sort_dropdown)
```

This wraps the WebElement in Selenium’s dropdown helper.

```python
.select_by_value(value)
```

This selects the option whose HTML `value` attribute matches the given value.

Example SauceDemo options:

```html
<option value="az">Name (A to Z)</option>
<option value="za">Name (Z to A)</option>
<option value="lohi">Price (low to high)</option>
<option value="hilo">Price (high to low)</option>
```

So:

```python
Select(sort_dropdown).select_by_value("az")
```

selects:

```text
Name (A to Z)
```

And:

```python
Select(sort_dropdown).select_by_value("lohi")
```

selects:

```text
Price (low to high)
```

### Other useful `Select` methods

```python
select.select_by_visible_text("Name (A to Z)")
select.select_by_index(0)
select.select_by_value("az")
```

For this framework, `select_by_value` is nice because values like `az` and `lohi` are short and stable.

### Important limitation

`Select` only works with real HTML `<select>` tags.

If a website uses a custom dropdown built with `<div>` and `<ul>/<li>`, `Select` will not work. Then we would need normal Selenium clicks.

### Interview answer

> I used Selenium’s Select helper because the SauceDemo sort control is a real HTML select element. I wait for the dropdown to be visible, wrap it in Select, and choose the option by value, such as `az` for name A to Z or `lohi` for price low to high. This is cleaner and more reliable than manually clicking dropdown options.

## 8. Product Name Extraction Explanation

Example method:

```python
def get_product_names(self) -> list[str]:
    products = self.driver.find_elements(*self.PRODUCT_NAMES)
    return [product.text for product in products]
```

### Breakdown

```python
self.driver.find_elements(*self.PRODUCT_NAMES)
```

returns a list of matching WebElements.

If:

```python
PRODUCT_NAMES = (By.CLASS_NAME, "inventory_item_name")
```

Then:

```python
*PRODUCT_NAMES
```

unpacks the tuple into:

```python
By.CLASS_NAME, "inventory_item_name"
```

### List comprehension

```python
[product.text for product in products]
```

means:

```text
For each WebElement in products, get its visible text.
Return all those texts as a list.
```

Equivalent beginner-friendly version:

```python
names = []

for product in products:
    names.append(product.text)

return names
```

## 9. Product Price Extraction and Parsing Explanation

Example method:

```python
def get_product_prices(self) -> list[float]:
    prices = self.driver.find_elements(*self.PRODUCT_PRICES)
    return [
        float(price.text.replace("$", ""))
        for price in prices
    ]
```

### Why parsing is needed

The UI text is:

```text
$7.99
$15.99
$49.99
```

This is string text, not numeric data.

To compare low-to-high order properly, convert each displayed price into a number.

### Step-by-step

```python
price.text
```

Example:

```text
"$7.99"
```

```python
price.text.replace("$", "")
```

becomes:

```text
"7.99"
```

```python
float("7.99")
```

becomes:

```python
7.99
```

### Why not compare price strings?

String comparison can produce misleading order because it compares characters lexicographically, not numeric values.

Example:

```python
sorted(["$7.99", "$15.99"])
```

may not reflect true numeric sorting because it compares text character by character.

### Interview note

For this demo framework, `float` is acceptable because we only compare display order. In financial calculations, `Decimal` would be safer.

## 10. `sorted()` Explanation

### User question

What does this achieve?

```python
actual_product_prices == sorted(actual_product_prices)
```

### Explanation

`sorted(actual_product_prices)` creates a **new sorted copy** of the list.

Example:

```python
actual_product_prices = [7.99, 9.99, 15.99, 29.99, 49.99]

sorted(actual_product_prices)
```

returns:

```python
[7.99, 9.99, 15.99, 29.99, 49.99]
```

So:

```python
assert actual_product_prices == sorted(actual_product_prices)
```

means:

> The prices displayed in the UI should already be in the same order as Python’s sorted version of those prices.

If UI order is wrong:

```python
actual_product_prices = [49.99, 7.99, 15.99, 9.99]
```

Then:

```python
sorted(actual_product_prices)
```

returns:

```python
[7.99, 9.99, 15.99, 49.99]
```

The assertion fails.

### Important detail

`sorted()` does **not** modify the original list.

```python
prices = [49.99, 7.99, 15.99]

sorted_prices = sorted(prices)

print(prices)         # [49.99, 7.99, 15.99]
print(sorted_prices) # [7.99, 15.99, 49.99]
```

### Does `sorted()` use ascending order by default?

Yes.

For numbers:

```python
sorted([49.99, 7.99, 15.99])
```

returns:

```python
[7.99, 15.99, 49.99]
```

For descending order:

```python
sorted([49.99, 7.99, 15.99], reverse=True)
```

returns:

```python
[49.99, 15.99, 7.99]
```

### Interview answer

> I extract the prices displayed in the UI, convert them to numbers, and compare the actual UI order with Python’s sorted copy of the same list. Since sorted is ascending by default, this checks whether the UI is already sorted from low to high.

### Marker choice

```python
@pytest.mark.regression
```

### Why smoke?

Logout is part of the core session lifecycle. A build where users can log in but cannot log out has an important session-level problem.

### Why keep logout in `InventoryPage`?

We considered whether to create:

```text
pages/menu_component.py
```

But decided not to.

Reason:

- The side menu is currently only used for logout.
- A component abstraction would be premature.
- If future tests use the menu for reset app state, about page, etc., then `MenuComponent` can be introduced.

### Expected implementation style

```python
MENU_BUTTON = (By.ID, "react-burger-menu-btn")
LOGOUT_LINK = (By.ID, "logout_sidebar_link")

def open_menu(self):
    self.click(self.MENU_BUTTON)

def logout(self):
    self.open_menu()
    self.click(self.LOGOUT_LINK)
```

### Login page verification

A good `LoginPage.is_loaded()` checks visible login form elements:

```python
def is_loaded(self) -> bool:
    return (
        self.is_visible(self.USERNAME_INPUT)
        and self.is_visible(self.PASSWORD_INPUT)
        and self.is_visible(self.LOGIN_BUTTON)
    )
```

### Interview answer

> In PR18, I added logout as a smoke/regression check to complete the authenticated session lifecycle. The test uses the logged-in fixture, logs out through the inventory page menu, and verifies that the login page is visible again. I kept the menu logic in InventoryPage for now to avoid premature abstraction.

## 12. PR Review Best Practices Discussed

When reviewing automation PRs, check:

### Test value

```text
Does this scenario matter?
Is it stable and repeatable?
Is it correctly marked as smoke/regression/negative/e2e?
```

### Test readability

```text
Can I understand the scenario from the test name and test body?
Are setup, action, and assertion clear?
Is the test too broad?
```

### Page Object Model

```text
Are locators inside page objects?
Are UI actions inside page objects?
Are assertions mostly in tests?
Are method names user-action oriented?
```

### Selenium reliability

```text
Are explicit waits used?
Are hard sleeps avoided?
Are locators stable?
Is dropdown handling appropriate?
Is there any animation/timing issue?
```

### Fixtures

```text
Does the test use existing fixtures instead of repeating setup?
Is the fixture hiding too much behavior?
Is test state isolated?
```

### Data and parametrization

```text
Is parametrization used where cases share the same flow?
Are ids readable?
Is external data justified?
Is there unnecessary branching inside the test?
```

### Debuggability

```text
Are assertion messages useful?
Will screenshots/logs help diagnose failure?
Are generated artifacts ignored?
```

### Maintainability

```text
Is the PR focused?
Is there duplicated code that should become a helper?
Is there over-abstraction?
Are names consistent?
```

## 18. Strong Interview Answers to Preserve

### Why Page Object Model?

> Page Object Model separates page interaction logic from test scenario logic. Tests describe what behavior is being validated, while page classes handle locators and UI actions. This improves maintainability because UI changes can often be fixed in one page class instead of across many tests.

### Why fixtures?

> Fixtures separate setup and teardown from test logic. In this framework, fixtures manage browser lifecycle, config loading, and reusable preconditions like logged-in inventory state.

### Why explicit waits?

> Explicit waits wait for meaningful UI conditions like visibility or clickability. This is more reliable than hard sleeps because it adapts to actual page state instead of pausing blindly.

### Why parametrization?

> Parametrization lets one test function run with multiple input combinations. It reduces duplicate code and makes negative validation cases easier to review.

### Why JSON and Excel?

> JSON is clean and reviewable in Git, while Excel is familiar for QA-style tabular data. I included both to demonstrate different data-driven strategies while keeping each test path readable.

### Why screenshots and logs?

> Screenshots and logs improve debuggability. When a Selenium test fails, they help determine whether it is a product defect, test issue, locator problem, timing issue, or environment problem.

### Why Allure?

> Allure provides structured test execution results that are easier for a team to review than raw console output. I started with basic result generation and left advanced attachments for later to keep the PR focused.

### Why Gitea?

> I used local Gitea to simulate a realistic team workflow with multiple contributors, feature branches, PRs, reviews, and protected main. This helped me practice the collaboration and review side of automation engineering.

### How would you review a contractor PR?

> I would check whether the test adds value, uses stable locators, avoids hard sleeps, has meaningful assertions, follows Page Object Model, uses fixtures correctly, avoids unnecessary duplication, handles data clearly, and provides enough debug information through logs or screenshots.

### How would you help a manual QA engineer transition into automation?

> I would start from their manual test case understanding, choose stable repetitive high-value scenarios, pair on the first few tests, explain POM through familiar manual steps, review PRs constructively, and document reusable examples so the team can grow sustainably.
